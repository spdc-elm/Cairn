# V3.2 Execution Ledger Requirements

日期：2026-05-20
状态：需求草案，已按第一性原理重审
依据：用户提出的 output 实时跟踪、resume 本地可见、fork 多轮连续三项问题；本轮读取的 `cairn/src/cairn/server/schema.py`、`cairn/src/cairn/server/migrations/{0002,0003,0005}.py`、`cairn/src/cairn/server/questions/{models,manager}.py`、`cairn/src/cairn/server/routers/{questions,runs}.py`、`cairn/src/cairn/server/services.py`；在 `pentestVM` 内对 `pi 0.73.0`、`codex-cli 0.118.0`、`Claude Code 2.1.142` 的命令行验证；三名独立 subagent 的架构审查意见。

## 1. 核心判断

上一版 `anchor -> turns -> executions` 比当前实现清楚，但仍停留在 Output/Question 层。更底层地看，Cairn 应以一次 worker run 为物理事实原子：

```text
Project
  -> Intent          工作订单：要探索什么
  -> ExecutionRun    审计脊柱：某 worker 实际跑了一次
  -> ExecutionEvent  唯一实时事件流
  -> Branch          可继续的 session / conversation 线
  -> Fact            知识黑板：一次探索进入 DAG 的结果节点
  -> Artifact        证据与产物
```

简化原则：

- `ExecutionRun` 是最小 provenance 单位；session、stdout、report、returncode、worker identity 都挂在 run 上。
- `ExecutionEvent` 是实时 Output / Conversation 的唯一事件源；UI 不再拼 `run_provenance + question_jobs + question_events`。
- `Intent` 不是纯 view。它是工作订单，表达“要探索什么”和调度偏好；实时租约、heartbeat、取消、失败重试属于 `ExecutionRun`。
- `Fact/Intent DAG` 是产品本体，不被 `ExecutionRun` 替换。
- `Fact` 不是 atomic assertion，而是一次探索步骤进入黑板后的 result node；候选结论不新增 `Claim` 核心概念，首版用 execution event / artifact 承载。
- `Branch` 是 fork/resume 的对象；多轮对话就是同一 branch 下追加 execution。
- 旧 DB 兼容不是目标。允许提供一次性备份 + destructive reset migration，换取长期可维护性。

严判：execution-first 对，execution-only 错。Cairn 不能退化为日志系统；它需要 execution 做审计和运行租约底座，Fact/Intent DAG 做用户心智模型，artifact 做证据层。

## 2. 当前问题的根因

### 2.1 事实源重复

当前 schema 中：

- `run_provenance` 同时保存 run identity、remote session、question anchor、source run、session effect。
- `question_threads` 再保存 anchor、source run、source remote session、worker identity、mode、session effect。
- `question_jobs` 又保存 mode、message、run_log_id、question remote session、execution identity。
- `question_events` 另存一套 question event。
- filesystem JSONL run log 再保存 stdout/stderr/status events。

结果是同一件事被拆在多处：一次 worker execution 既是 run provenance，又可能是 question job，又有 JSONL，又有 question events。

### 2.2 调度租约挂错层

当前 `intent` 是图边、待办、租约三合一：`intent_sources/to_fact_id` 表达 graph 关系，`worker/last_heartbeat_at/control_state` 又表达正在运行的 worker lease。

这会让一个语义对象承担运行时并发控制。更稳的方向是：

```text
Intent = work order
ExecutionRun = lease / heartbeat / cancel / retry / status
```

同一 intent 可以有多次 execution：retry、不同 worker 探索、conclude phase 都应各自可追踪。

### 2.3 intent/fact 与 run 的依赖倒置

当前 Output 和 Ask capability 往往从 `fact` / `intent` 反查 successful `run_provenance`。这导致 running intent 在未成功前看不到 Output，刷新时出现 `provenance id 不存在`。

正确方向应是：

```text
ExecutionRun -> Fact / Artifact / Branch projection
```

而不是让图节点负责找回底层运行日志。

### 2.4 fork/resume 被建成 question 特例

fork/resume 的本质不是 question thread，而是 session lineage：

```text
branch + latest remote_session_out -> next execution.remote_session_in
```

当前以 `question_threads.source_session` 和 `question_jobs.question_session` 表达，会自然滑向单轮 fork：后续 job 仍可能从 source session 重新开始，而不是沿 branch 继续。

## 3. Harness 验证事实

### 3.1 Pi

- `pi --fork <base_session>` 会输出新的 `session` event。
- 后续 `pi --session <fork_session>` 能继续 fork session 的上下文。
- 因此 Pi 支持 headless fork + fork continuation。

### 3.2 Claude Code

- `claude --resume <base> --fork-session -p ...` 会输出新的 `session_id`。
- 后续 `claude --resume <fork_session> -p ...` 能继续 fork session 的上下文。
- 因此 Claude Code 支持 headless fork + fork continuation。

### 3.3 Codex

- `codex exec --json` 会输出 `thread.started`。
- `codex exec resume --json <thread_id>` 能继续上下文。
- `codex fork <thread_id> <prompt>` 在非 TTY 下失败：`stdin is not a terminal`。
- 因此当前 Codex 只应声明 headless resume，不应声明 headless fork。

## 4. 方案对比

### 4.1 保守方案：修补 Question Timeline

保留 `question_threads/jobs/events`，补 `GET /conversation`，让 UI 拼出 source run + question runs。

优点：短期改动小。

问题：仍有两套事实源。每次新增展示需求都会继续补字段、补 join、补兼容逻辑。

结论：不推荐。它能缓解症状，但会延续当前熵增。

### 4.2 激进方案：Pure Execution Graph

只保留 `Execution`、`Event`、`Edge`、`Artifact`。Intent、Fact、Conversation、Branch 全部由 graph query 派生。

优点：理论统一。

问题：产品语义过薄。调度、用户心智、知识接受状态都会变成 path resolution 问题。

结论：不推荐首版。它优雅，但会把 Cairn 做成研究型图系统，而不是稳定可用的协作黑板。

### 4.3 推荐方案：Fact/Intent DAG + Execution Ledger

核心实体：

- `Intent`：work order，不持有 live worker lease。
- `ExecutionRun`：一次 worker execution。
- `ExecutionEvent`：run 内 append-only event stream。
- `Branch`：可继续的 conversation/session timeline。
- `Fact`：已进入黑板的知识节点。
- `Artifact`：report、transcript、scan output、file、screenshot 等证据。

事实源：

- 实时输出与对话文本来自 `ExecutionEvent`。
- session 连续性来自 `ExecutionRun.remote_session_in/out`。
- 图上 fact 来自明确创建的 `Fact` 记录。一个成功 concluded 的探索 intent 应产生一个 primary result fact。
- 证据来自 `Artifact` 与 `EvidenceLink`。

结论：推荐。它承认 execution 是底层原子，但保留 fact/intent/artifact 这几个不可省的产品语义。

## 5. 目标

1. Output 面板可实时显示 running execution 的事件流，刷新后继续从 cursor 追进度。
2. Resume 后远端 session 的新增回复同步为本地 execution events，并出现在同一 branch timeline。
3. Pi / Claude Code fork 支持多轮连续追问；Codex 不开放 headless fork。
4. 所有 worker 运行都统一落为 `ExecutionRun + ExecutionEvent`，不再区分普通 run log、question job log、question event log。
5. Graph 上的 fact/intent 展示保持 CAIRN 原有心智模型，但不再反向承担 run/session 的事实源职责。

## 6. 非目标

- 不维护旧 `question_threads/jobs/events/run_provenance` 的长期兼容 API。
- 不把 Codex top-level fork 做成 PTY/TUI 自动化。
- 不实现 WebSocket/SSE 首版强依赖；cursor polling 足够。
- 不把远端 CLI 原生 session 文件同步回 Cairn DB；只记录 session id/kind/status 与本地事件。
- 不把所有 worker 输出自动变成 fact；未进入黑板的候选结论先留在 execution event / artifact 中。

## 7. 核心数据模型

### 7.1 Intent

工作订单，不是 view，也不是 worker 租约。

字段语义：

- `id, project_id`
- `source_fact_ids[]`
- `description`
- `state`: `open | concluded | withdrawn`
- `requested_worker, timeout_seconds`
- `created_by, created_at, concluded_at`
- `concluded_fact_id` 可选

一个 intent 可对应多次 execution：retry、并发 worker、conclude phase 都不应压成一条。

`running` 不是 intent 的基础状态；它是存在 active `ExecutionRun(intent_id=...)` 的派生视图。取消、heartbeat、lease expiry 不写在 intent 上。

### 7.2 ExecutionRun

一次 worker execution，最小 provenance 单位。

字段语义：

- `id`
- `project_id`
- `intent_id` 可空；question/fresh/reason 可以没有 intent。
- `branch_id` 可空；对话/fork/resume execution 归属某 branch。
- `parent_execution_id` 可空；fork、retry、conclude 可表达 lineage。
- `task_type`: `explore | conclude | reason | question | healthcheck`
- `phase`: `run | conclude | followup | healthcheck`
- `worker_name, worker_type, environment_id, endpoint_id, model_profile_id, workspace`
- `status`: `pending | leased | running | succeeded | failed | cancelled`
- `leased_by, leased_at, lease_expires_at, last_heartbeat_at`
- `control_state, control_requested_at, control_reason`
- `remote_session_in_kind/id/status`
- `remote_session_out_kind/id/status`
- `input_snapshot_json`
- `started_at, finished_at, returncode, error_code, error_detail`

`run_log_id` 不再定义 execution 身份；若保留文件 JSONL，文件路径只是 `Artifact(type=transcript)` 或 execution 的 storage detail。

### 7.3 ExecutionEvent

append-only 事件流，是 Output 和 Conversation 的唯一实时事实源。

字段语义：

- `id`
- `execution_id`
- `project_id`
- `seq`
- `cursor`
- `ts`
- `event_type`: `status | stdout | stderr | message | tool | artifact | fact_candidate | session | metric`
- `role`: `user | assistant | system | tool` 可空
- `payload_json`

约束：

- 同一 execution 内 `seq` 单调递增。
- UI 增量读取使用 `cursor`。
- projections 可缓存，但不得成为事实源。

### 7.4 Branch

可继续的 session / conversation timeline。

字段语义：

- `id`
- `project_id`
- `source_execution_id`
- `parent_branch_id` 可空
- `anchor_kind/id` 可空，仅用于 UI 从图节点进入。
- `mode`: `source | resume | fork | fresh_context`
- `worker identity` 可选，用于锁定同一 harness 能力。
- `status`
- `created_at, updated_at`

下一轮 execution 的 session 由 branch 最近成功 execution 的 `remote_session_out` 推导，不在 branch 上重复存 `current_session`。

### 7.5 Fact

知识黑板的内部核心，也是用户 DAG 中的节点。

定义：

- `Fact` 不是最小事实断言，也不是所有观察的原子集合。
- `Fact` 是一次探索步骤进入黑板后的结果节点，承载这次 intent 执行对用户有用的摘要。
- 如果一次执行发现了多个点、没有进展、失败但形成了明确结论，都仍应汇总为一个 result fact。
- 细粒度观察、原始日志、证据、长 report 放在 `ExecutionEvent` / `Artifact`，不拆成多个图节点。

字段语义：

- `id, project_id`
- `kind`: `origin | goal | fact | observation | negative_result`
- `status`: `active | superseded | retracted`
- `title, text`
- `produced_by_execution_id` 可空
- `produced_by_intent_id` 可空
- `confidence/uncertainty` 可选
- `created_at`

约束：

- 成功 concluded 的探索 intent 应有且仅有一个 primary result fact，并写入 `intent.concluded_fact_id`。
- 并非所有 execution 都产 fact：question、healthcheck、失败重试、resume/fork follow-up 可只产 event/artifact。
- 一个 execution 可以包含多条观察，但图层默认只新增一个 result fact，避免 UI 和操作模型碎片化。
- 若未来需要“待审核候选事实”的长期 workflow，再考虑把 `Fact(status=proposed)` 或 `Claim` 升格；V3.2 不引入 `Claim`。

### 7.6 Artifact 与 EvidenceLink

Artifact 存证据和大产物：

- `id, project_id`
- `produced_by_execution_id`
- `type`: `report | transcript | scan | file | screenshot | other`
- `uri/path/content_hash`
- `summary`
- `created_at`

EvidenceLink 表达支持关系：

- `fact_id`
- `artifact_id` 可空
- `execution_id` 可空
- `relation`: `supports | contradicts | derived_from`

## 8. API 需求

### 8.1 Execution API

```http
POST /projects/{project_id}/executions
GET  /projects/{project_id}/executions/{execution_id}
GET  /projects/{project_id}/executions/{execution_id}/events?after_cursor=...
POST /dispatcher/executions/{execution_id}/events
PATCH /dispatcher/executions/{execution_id}
```

用于普通 worker run、question run、reason run、healthcheck run 的统一生命周期。

### 8.2 Branch / Conversation API

```http
POST /projects/{project_id}/branches
GET  /projects/{project_id}/branches/{branch_id}/timeline?after_cursor=...
POST /projects/{project_id}/branches/{branch_id}/messages
POST /projects/{project_id}/branches/{branch_id}/fork
```

语义：

- `messages` 创建新的 question execution。
- `fork` 从指定 branch cursor 或 execution 创建子 branch。
- timeline 只是 projection：按 branch 下 executions + events 生成。

### 8.3 Graph Projection API

现有 fact/intent 图 UI 应改为读取 semantic projection：

```http
GET /projects/{project_id}/graph
POST /projects/{project_id}/facts
PATCH /projects/{project_id}/facts/{fact_id}
POST /projects/{project_id}/intents
```

UI 与内部核心都保留 facts/intents。区别只在于：runtime state 不再塞进 facts/intents。

## 9. 用户流程

### 9.1 Running Output

1. Dispatcher lease intent 后创建 `ExecutionRun(status=running)`。
2. Worker stdout/stderr/message 持续 append `ExecutionEvent`。
3. UI 打开 Output 时按 execution 或 branch 读取 events。
4. 刷新后用 cursor 继续，不再依赖 successful provenance。

### 9.2 Resume

1. UI 对 branch 或 source execution 发起 resume message。
2. Server 创建同 branch 下的新 `ExecutionRun(task_type=question, mode=resume)`。
3. `remote_session_in` 来自 source execution 或 branch 最近 session。
4. Worker 完成后写 `remote_session_out` 与 assistant message events。
5. Output timeline 从 events 投影出完整问答。

### 9.3 Fork 多轮

1. UI 从 source branch/execution 创建 fork branch。
2. 第一轮 execution 使用 source `remote_session_out` 作为 `remote_session_in`，并让 harness fork。
3. 后续消息都追加到 fork branch。
4. 每轮新 execution 使用上一轮成功 execution 的 `remote_session_out`。

## 10. DB / 迁移策略

V3.2 不要求保留旧 DB 兼容。

推荐策略：

1. 启动前备份当前 `cairn.local.db`。
2. 新增 destructive schema migration 或显式 `cairn db reset --to v3.2`。
3. 新 schema 只保留必要旧概念：project、environment、worker inventory、health。
4. 删除或停止使用：
   - `run_provenance`
   - `question_threads`
   - `question_jobs`
   - `question_events`
   - `question_resume_locks`
   - `intents.worker / last_heartbeat_at / control_state` 等 live lease 字段
5. 测试环境优先用 fresh DB 验证。

若需要保留少量旧实验数据，只做一次性 best-effort import，不为旧模型保留长期代码路径。

## 11. 验收标准

1. running intent 的 Output 在任务未完成时显示 events；浏览器刷新后继续追进度。
2. 对同一个 Pi source branch 连续 fork 两轮，第二轮能记住第一轮上下文。
3. 对同一个 Claude Code source branch 连续 fork 两轮，第二轮能记住第一轮上下文。
4. Codex UI 不展示 Fork；Resume 可用。
5. 对同一个 source session 做两次 resume，远端记忆与 Cairn 本地 timeline 一致。
6. worker run、question run、reason run 均可在 `executions` 中查询，且 stdout/stderr/message 均来自 `execution_events`。
7. 每个 successful concluded exploration intent 产出一个 primary result fact；该 fact 能追溯到 producing execution 与 artifact。
8. 全量测试通过：`env PYTHONPATH=cairn/src python -m pytest cairn/tests -q`。
