# V3.3 Frontend Refactor Requirements

日期：2026-05-20
状态：需求草案
依据：用户提出 server 前端臃肿、不可维护，要求在展示能力和效果基本不变的前提下做 v3.3 前端重构 spec；本轮读取 `README.md`、`docs/specs/v2-command-blackboard-requirements.md`、`docs/specs/v3-interactive-worker-qna-requirements.md`、`docs/specs/v3.2-live-conversation-thread-requirements.md`、`docs/plan/v3.2-live-conversation-thread-execution-plan.md`、`cairn/src/cairn/server/static/index.html`、`cairn/src/cairn/server/routers/{projects,executions,branches,runs,questions,environments,workers}.py`、`cairn/src/cairn/server/schema.py`、`cairn/tests/server/test_environment_healthcheck_ui_guard.py`、现有测试目录；并吸收三名 subagent 从架构、测试、体验信息架构角度的只读审查。

## 1. 核心判断

v3.3 的本质不是“把一个大 HTML 拆成多个文件”，也不是“换前端框架”。真正问题是前端承担了过多产品语义、运行事实解释、worker transcript 解析、轮询生命周期和 UI 状态协调。

重构第一性原则：

- 用户心智模型不变：`Fact/Intent DAG` 仍是主工作面。
- 运行事实源不变：`ExecutionRun + ExecutionEvent + Branch` 是 Output、Conversation、Ask 的事实源。
- 展示能力基本不变：以用户可见工作流与语义不退化为准，不要求像素级一致。
- 可维护性优先：前端必须按产品语义和状态边界拆分，不能只做机械切文件。
- 测试先行：先冻结 API contract、前端纯函数、浏览器 smoke 与视觉 smoke，再大规模改结构。

一句话：v3.3 要把 UI 从“全能脚本”改成“薄渲染层 + 明确 projection contract + 可测状态模块”。工作量不是约束，语义不退化才是约束。

## 2. 背景与现状

当前 Web UI 由一个约 5457 行的 `cairn/src/cairn/server/static/index.html` 承载。该文件同时包含：

- HTML 模板、Tailwind 配置、全局样式、动画、modal、项目列表、图视图、侧栏、环境面板、设置面板。
- 一个 `cairnApp()` Alpine store，负责路由、API client、项目状态、graph selection、conversation、question branch、run log、replay、healthcheck、local prefs、modal lifecycle。
- Cytoscape graph model 与 layout 策略。
- ExecutionEvent 到 ConversationEvent 的前端投影。
- Pi/Claude/Codex 风格 JSON stdout 的部分浏览器端解析。
- 多套轮询：项目级、conversation、run log、question thread、healthcheck。

已核实的维护性问题：

1. 边界坍缩。
   `cairnApp()` 同时是 view model、domain service、API client、parser、scheduler、renderer。任何局部改动都可能影响图、Output、Ask、Log、环境设置。

2. 事实源解释外溢到前端。
   前端仍在若干路径中根据 execution events、stdout JSON、branch timeline、intent 字段自行推导 transcript 与运行态。这与 v3.2 要求的 “ExecutionEvent 是实时输出唯一事实源” 容易分裂。

3. API projection contract 不够硬。
   `/projects/{project_id}/graph` 已承担 UI projection 角色，但当前契约仍偏隐式。前端依赖 `active_execution_id`、`latest_execution_id`、`runtime_status`、`producing_execution_id` 等字段，需正式纳入 contract。

4. selection 锚点高风险。
   图、Detail、Output、Ask、Log、Replay 都围绕当前选中对象运转。若重构拆组件但不先定义 selection model，最容易出现“图选的是 A，Output 看的是 B，Ask 发到 C”的错锚。

5. 测试护栏不足。
   现有 UI 测试主要是字符串守卫，能防止删错关键调用，但不能证明浏览器可运行、Alpine 初始化正常、graph canvas 非空、点击行为有效、布局无遮挡。

## 3. 目标

v3.3 目标如下：

1. 保持当前前端展示能力和效果基本不变。
   允许视觉微调、DOM 重组、文件拆分、构建方式变化；不允许核心工作流、状态语义、可见信息、交互入口退化。

2. 建立明确前端架构边界。
   UI 应分为 API/projection contract、domain view model、state stores、render components、graph renderer、event renderer、polling/subscription、local preferences 等层。

3. 让前端成为运行事实的消费者，而非解释源。
   Worker transcript normalization、execution status、branch availability、fork/resume/fresh_context 可用性应来自 server/shared contract；前端只做标准 view model 渲染。

4. 先补测试，再重构。
   重构前必须补足 contract tests、前端纯函数 golden tests、browser E2E smoke、visual smoke。没有这些护栏，不进入大规模结构调整。

5. 支持后续演进。
   v3.3 后应能较低风险地继续优化 UI、引入构建工具或框架、替换 graph renderer、扩展 Output/Timeline，而不再改一处牵全身。

## 4. 非目标

- 不改变 Cairn 产品本体，不重定义 `Fact`、`Intent`、`ExecutionRun`、`ExecutionEvent`、`Branch`、`Artifact`。
- 不把 UI 改成 landing page、解释页或 marketing 页面；首屏仍是工作面板。
- 不在 v3.3 里新增核心后端能力；后端只补 UI projection contract 与必要 normalization contract。
- 不以像素级一致作为验收目标；以语义、工作流、可见状态、可操作性一致为准。
- 不用“换框架”掩盖边界问题。是否引入 Vite/TypeScript/React/Vue/Svelte/Alpine 模块化，属于 planning 阶段技术选型；spec 只规定架构要求。
- 不允许为兼容重构而恢复旧 `/questions`、`/runs/*/transcript` 作为 Output/Conversation 主路径。
- 不允许让前端按 worker type 硬编码 fork/resume 能力。

## 5. 用户流程

### 5.1 项目列表

用户打开根页面后仍看到项目列表：

- 项目数量、active/stopped/completed 状态统计。
- reason running、working intent、环境徽标。
- 新建项目、打开项目、重命名、停止/恢复、重开、删除、Snapshot。
- 全局 Stop Active、Environment 面板、Settings/Local prefs。

### 5.2 Graph 工作面板

用户打开项目后仍以 Fact/Intent DAG 为中心：

- origin、goal、fact、open intent、running intent、unclaimed intent、concluding、conclude_failed、bootstrap 状态可辨识。
- 支持布局切换、fit、侧栏拖拽、replay。
- 点击 fact 显示上游 lineage；点击 intent/edge 显示相关 from/to；Shift 多选 fact 后可创建 intent 或 complete。
- 图、右侧 Detail、Output、Log、Replay 必须围绕同一 selection anchor 同步。

### 5.3 Detail / Settings / Hints / Log

右侧面板继续承担项目操作面：

- Detail：显示 fact/intent 元信息、producing intent/execution、report path、编辑 fact、intent 操作。
- Settings：项目级 auto_reason、allowed workers、timeouts。
- Hints：查看、添加、删除 hints。
- Log：项目叙事时间线，点击 log 能反向定位图节点或 execution；Replay 仍从 timeline 投影。

### 5.4 Output / Conversation

用户从 fact 或 intent 进入 Output：

- running intent 未完成也能看到实时 events。
- completed fact/intent 默认锚到 producing/latest execution。
- Messages、Tools、Raw 三视图保留。
- 刷新后仍能从 cursor 或重新读取 events 继续显示。
- 无 provenance 或旧数据缺失时明确显示 missing reason，并保留 Fresh Context。
- Raw fallback 必须保留，作为 parser 失败、worker 协议漂移、长工具输出调试时的最后可信界面。

### 5.5 Ask

用户可对结束对象或有 source execution 的对象提问：

- Fork/Resume/Fresh Context 的可用性来自 server projection：worker capability + source execution session + runtime health。
- Fork 可用时默认优先；多轮 fork 在临时 branch 下连续。
- Resume 必须显式确认，并进入主 Output/branch timeline。
- Fresh Context 在无 session 时仍可用，但 UI 明示不是原 session。
- running intent 不应错误展示 fork ask。

### 5.6 Environment / Worker Health

Environment 面板继续支持：

- 环境和 endpoint CRUD。
- healthcheck request 队列化。
- pending/running/succeeded/failed 分层状态。
- 不把 delegated/queued 当最终健康结果。
- worker capability 与 runtime health 在 UI 中可见，并影响 Ask action availability。

## 6. 功能需求

### 6.1 架构分层

前端重构后至少应具备以下逻辑边界。具体文件名留给 planning，但边界不可混淆：

- `ApiClient`：只负责 HTTP、错误规范化、JSON/text 读取。
- `ProjectionContracts`：描述 server 返回的 UI projection shape；若使用 TypeScript，应以类型表达；若仍用 plain JS，应有 runtime shape checks 或 tests。
- `ProjectStore`：项目列表、当前项目、项目级 polling、项目生命周期动作。
- `GraphSelectionStore`：fact/intent/multi-fact/timeline selection，产出唯一 `conversationAnchor`。
- `GraphModelAdapter`：把 semantic projection 转为 Cytoscape nodes/edges，不做 DOM 与 HTTP。
- `GraphCanvas`：只负责 Cytoscape 初始化、layout、highlight、resize、focus。
- `ExecutionStreamStore`：读取 execution events、cursor、polling、active/idle 退避、取消。
- `ConversationViewModel`：把标准 event view model 分为 Messages/Tools/Raw。
- `QuestionBranchStore`：fork/resume/fresh_context branch、composer、active execution、resume confirmation。
- `TimelineStore`：project narrative log、selection parity、replay frames。
- `EnvironmentStore`：environment/endpoint/healthcheck request。
- `LocalPrefsStore`：layout、side panel width、actor name 等本地偏好。

这些边界可由 Alpine modules、ES modules、Web Components、React/Vue/Svelte 组件或其它轻量方式实现；spec 不指定框架。

### 6.2 UI Projection Contract

Server 必须为 UI projection 提供稳定 schema。当前 `/projects/{project_id}/graph` 已不只是 graph 数据，而是混合了 project、facts、intents、execution projection、worker capability、timeline/replay 所需字段。更准确的命名应是：

```http
GET /projects/{project_id}/ui-projection
```

`/graph` 可在过渡期保留为兼容 alias，但新前端主路径应读 `/ui-projection`。这个命名减少误导：graph 只是 UI projection 的一个视图，不是 projection 的全部。

最小 schema 至少包含：

```text
ProjectUiProjection
- project
- facts[]
  - id
  - title
  - description
  - metadata
  - producing_execution_id/null
  - produced_by_execution_id/null
  - artifact_summaries[]
- intents[]
  - id
  - from[]
  - to/null
  - description
  - creator
  - requested_worker/null
  - worker_name/null
  - runtime_status
  - active_execution_id/null
  - latest_execution_id/null
  - concluded_fact_id/null
  - blocked_reason/null
- hints[]
- timeline_summary or enough fields to build log/replay
- worker_capabilities/read model needed by Ask controls
```

要求：

- `/projects/{project_id}/ui-projection` 必须有明确 response model 或等价 contract tests。
- `/projects/{project_id}/graph` 若保留，只作为 compatibility alias，不再作为新代码命名基准。
- 前端不得再依赖未记录的裸 dict 附加字段。
- intent running/concluding/failed 等 UI 状态应从 execution projection 派生，不以 `intent.worker`、`last_heartbeat_at`、`control_state` 作为事实源。
- Fact/Intent DAG 仍保留，不被 execution list 替代。

### 6.3 Execution / Conversation 渲染

前端只能渲染标准化事件 view model，不应在主路径解析 worker 私有 stdout JSON。

允许：

- 前端把 server 返回的标准 `ExecutionEventView` 映射成 message/tool/raw UI。
- Debug Raw 面板展示不可解析内容。
- 过渡期保留前端 parser，但必须标记为 legacy/debug fallback，并由 tests 防止其成为主路径。

不允许：

- UI 直接按 Codex/Pi/Claude stdout schema 推导产品语义。
- 同一 execution 在 Output、RunLog、Timeline、Healthcheck 中各自写一套状态推导。
- Conversation 绕过 `ExecutionEvent` 新建独立事实源。

### 6.4 Selection Parity

必须定义唯一 selection model：

```text
graphSelection
  -> selected object: fact | intent | multi_fact | none
  -> conversationAnchor: fact | intent | execution | branch | none
  -> timelineSelection: optional timeline entry
  -> graphFocus: node/edge set
```

验收要求：

- 点击 graph fact，Detail、Output、Log highlight 指向同一 fact。
- 点击 graph intent/edge，Detail、Output、Log highlight 指向同一 intent/execution。
- 点击 Log entry，Graph 居中并高亮对应对象，Output 不错锚。
- 切换项目、退出 replay、刷新页面后不保留跨项目错误 selection。

### 6.5 Polling / Subscription

前端需要统一异步读取模型：

- 每个 stream 有明确 owner、cursor、status、timer、cancel。
- 切换项目、切换 selection、关闭 panel、离开页面时取消旧 polling。
- running execution 默认 1s 级轮询；idle 可退避。
- 全局 project polling 不应覆盖正在编辑的 form 或破坏当前 scroll/selection。
- 后续可替换为 SSE/WebSocket，但 v3.3 不强制。

### 6.6 UI 展示 Parity

展示可改良，但能力不退：

- 项目列表、Graph、Detail、Output、Ask、Log、Settings、Hints、Environment 均保留。
- 长文本必须可读，不溢出按钮或卡片。
- Cytoscape canvas 必须非空且节点/边可读。
- 窄屏或小窗口下侧栏、modal、toolbar 不互相遮挡。
- 主要 action 的 disabled reason 或 unavailable reason 必须可见。

### 6.7 构建与部署

当前 MVP 由 `cairn serve` 直接提供内置 Web UI，用户无需单独启动前端 dev server。v3.3 可引入构建步骤，但必须满足：

- 生产运行仍由 `cairn serve` 提供静态产物。
- 源码与构建产物边界清晰。
- 构建命令、测试命令进入文档和 CI/本地验收。
- 不把 npm 生态依赖变成运行时必需，除非 planning 明确接受该取舍。

## 8. 关键决策点

### 8.1 是否引入现代前端工具链

可选方向：

- Alpine + ES modules：仍可成立，但更适合作为过渡层。优点是运行模型简单，和当前静态内置 UI 连续；缺点是大型交互状态、组件组合、测试隔离、类型约束都偏弱。若继续 Alpine，应强制把 store、pure functions、render fragments 拆开，否则只是“单文件变多文件”。
- React + TypeScript + Vite：最适合当前 v3.3 的长期维护目标。优点是组件边界、状态组合、测试生态、类型约束、复杂交互拆分能力强；Cytoscape 可被封装为 imperative island；Output/Ask/Timeline 这类状态复杂 UI 更容易做成可测组件。缺点是需要严控全局 store，否则会从 `cairnApp()` 变成一个更隐蔽的巨型 React app。
- Vue + TypeScript + Vite：适合渐进式迁移和模板表达，学习曲线较平滑，单文件组件对 UI 组织友好。缺点是复杂 domain state 仍需额外纪律，且生态与团队默认经验若不在 Vue 上，长期可维护性未必优于 React。
- Svelte + TypeScript + Vite：代码量少，响应式心智轻，适合内置工具型 UI。缺点是生态、招聘/协作惯性、复杂测试样例少于 React；Cairn 后续若发展成更大的操作台，React 的生态冗余反而更稳。
- Web Components / Lit：框架锁定较低，适合长期嵌入式 UI。缺点是复杂应用状态与测试体验不如主流框架直接，容易把复杂度转移到自建 glue code。

规格判断：若不考虑迁移工作量，只按长期可维护性排序，推荐 `React + TypeScript + Vite`。但前提是先定义 UI projection、selection reducer、execution stream store、question branch store；否则 React 只会把问题包装得更现代。任何框架选择都不得牺牲 `cairn serve` 的一体化运行体验，生产产物仍应由 server 静态托管。

### 8.2 Transcript normalization 放哪

推荐：server/shared 层负责 worker-specific normalization，前端只渲染标准 view model。

理由：

- server/dispatcher 已拥有 worker adapter 与 transcript parser 上下文。
- 前端解析 stdout 会导致协议漂移时出现多套事实解释。
- 后端 normalization 更容易被 unit/API tests 覆盖。

### 8.3 `/graph` 是否改名为 `/ui-projection`

推荐改名。理由：

- 当前返回值已包含 graph 以外的 UI 状态：execution identity、runtime status、worker/capability、artifact/replay 所需字段。
- `graph` 会误导后续实现者以为 endpoint 只服务 Cytoscape。
- `ui-projection` 更符合 v3.2 的架构：server 负责语义投影，front-end 负责消费与渲染。

过渡策略：

- 新增 `GET /projects/{id}/ui-projection` 作为主入口。
- 保留 `GET /projects/{id}/graph` 为 alias 或 deprecated endpoint。
- 新前端、测试、文档统一使用 `ui-projection` 命名。
- 若未来确实需要纯 graph endpoint，可另设 `GET /projects/{id}/fact-intent-graph`。

### 8.4 测试基线如何定义

展示能力基本不变不等于截图像素不变。验收应分层：

- contract：数据 shape 与语义不变。
- unit：纯逻辑不变。
- e2e：用户工作流不变。
- visual smoke：非空、可读、不遮挡、不溢出。

## 9. 验收标准

### 9.1 Contract / Unit

- `/projects/{id}/ui-projection` 有稳定 contract；facts/intents 的 execution projection 字段存在且语义明确。
- execution events cursor 支持增量、limit、非法 cursor、跨项目 cursor 检查。
- branch fork/resume/fresh_context contract 能返回稳定 unavailable reason。
- `buildElements` 能覆盖 origin/goal/fact、multi-source intent、open intent、running、unclaimed、concluding、conclude_failed、bootstrap。
- event view model 能覆盖 message、tool_call、tool_result、thinking、raw、error、run_started、run_finished。
- conversation compaction 能处理 delta、重复 event、terminal status。
- question availability 不按 worker type 分支。

### 9.2 Browser E2E

至少覆盖：

1. 打开根页面，项目列表空态和有项目态可用。
2. 创建项目，进入 graph，origin/goal 非空可见。
3. 多选 fact 创建 intent；图、Detail、Log 同步。
4. 模拟 running execution，Output 实时显示 events；刷新后仍显示。
5. completed fact/intent 的 Output 展示 Messages/Tools/Raw。
6. missing provenance 明示 fallback reason，Fresh Context 可用。
7. Fork 可用时可发起至少两轮临时 branch；关闭后不污染主 Output。
8. Resume 必须确认，确认后进入主 branch timeline。
9. Codex capability 下 Fork 不可点击或不展示，reason 可见；Pi/Claude capability 下 Fork 可用。
10. Environment healthcheck request 显示 pending/running/result，不把 queued 当最终成功。
11. Replay 开始、暂停、退出后 selection 和 project polling 正常。
12. 项目 stop/resume/reopen/delete 后列表与 header 状态一致。

### 9.3 Visual Smoke

桌面与窄屏至少截图检查：

- 空项目列表。
- 有项目列表。
- 小 graph。
- 多节点 graph。
- running Output。
- Ask thread。
- Environment console。
- Replay active。

自动断言：

- `#cy canvas` 非全白/透明。
- 主要容器无明显水平溢出。
- 侧栏 resize 后 graph 仍可用。
- 长标题、长 fact、长 tool output 不遮挡主要按钮。

### 9.4 Negative Guards

以下任一出现即不通过：

- UI 主路径调用 `/questions` 或 `/runs/*/transcript` 来展示 Output/Conversation。
- 前端主路径解析 worker-specific stdout JSON 来决定产品语义。
- Graph 显示 running，但 Output 找不到同一 execution。
- Server projection 标记 Fork unavailable，UI 仍允许点击 Fork。
- running intent 未完成时 Output 空白且无明确 pending/no events 状态。
- 刷新后丢失 running output。
- 点击 Log 反向定位到错误 graph object。
