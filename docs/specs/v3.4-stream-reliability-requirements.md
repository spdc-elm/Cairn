# V3.4 Stream Reliability Requirements

日期：2026-05-21
状态：需求草案
依据：用户实际测试反馈、dispatcher timeout 日志、`docs/architecture/cairn-architecture-ssot.md`、v3.2 live conversation 设计、当前 server/dispatcher/UI 代码只读审查、三路 subagent review。

## 1. 核心判断

这不是单一 worker、SSH 或 HTTP timeout 问题，而是 `ExecutionEvent` 主链路缺少端到端可靠性约束：

```text
worker stdout/stderr
  -> dispatcher EventSink / projector
  -> server append events
  -> execution terminal patch
  -> UI cursor polling / conversation projection
```

当前链路存在四类叠加失效：

1. server 写侧背压会让 `/dispatcher/executions/*/events`、claim、heartbeat 同时 read timeout。
2. dispatcher 可在事件尾部未可靠落库时 patch terminal status，导致 UI 以为 execution 已结束并停止追事件。
3. Conversation UI 对长 execution 只取头页或有限轮询，天然可能漏掉第 200 条之后的 final assistant/status。
4. worker-specific stdout JSONL 同时被 dispatcher projector 与 UI raw parser 解读，造成语义事件来源不唯一。

因此，修复目标不是“把 timeout 调大”，而是建立一条可恢复、可验收、不会静默丢 final 的可靠事件链。

## 2. 背景与现状

### 2.1 当前架构事实

SSOT 规定：

- `ExecutionEvent` 是 Output、Conversation、tool/message stream、stdout/stderr 的唯一主数据源。
- Dispatcher 负责将 worker 实时输出写入 `ExecutionEvent`。
- UI 必须从 execution/branch events 投影 Output/Conversation。
- streaming partial 应以稳定 key 压缩，terminal assistant message 必须覆盖 running partial，terminal status 不得让前端漏掉最后 assistant message。

### 2.2 当前代码事实

已核实的当前实现事实：

- `ExecutionEventSink` 将 worker stream 放入内存队列，后台 flush 到 `POST /dispatcher/executions/{execution_id}/events`。
- dispatcher HTTP client 默认 read timeout 为 10 秒；timeout 被转为 `ApiResult(status_code=0)`。
- flush 失败后 batch 会回到内存队列；队列无上限、无磁盘 spool、无 close 最大等待策略。
- `ExecutionEventSink.close()` 即使 drain 失败，仍可能继续 patch execution terminal status。
- `questions.py` 在 worker 结束后直接 append final assistant message，当前没有检查失败并重试；随后才 `sink.close()`。
- server append event 使用 `UNIQUE(execution_id, event_key)` 做幂等，但重复 key 不比对 payload。
- execution events cursor 是 project-scoped `evt_<project_seq>`；execution endpoint 接受同 project 的其他 execution cursor 时可能跳过目标 execution 的早期事件。
- Conversation UI 对 selected execution 初次只取 `/events?limit=200` 左右的头页；branch question polling 固定最多约 180 秒，而 question worker timeout 是 300 秒。
- UI 仍会把 raw stdout JSONL 解析成 message/tool/session，与 dispatcher projector 产生的标准 events 并存。
- SSH runner 读 stdout/stderr 以 `readline()` 为实时边界；无换行输出不会立即进入 event sink。

### 2.3 用户可见症状映射

- “Pi worker fork 回复只能收到半截”：可能由 UI 头页截断、question polling 180 秒停止、event flush 背压滞留、final append 静默失败共同造成。
- “聊天记录收着收着没有了，但远程还在继续干活”：可能由前端固定轮询上限、heartbeat/event 写请求同源背压、SSH 行缓冲、远端子进程逃逸造成。
- dispatcher 日志中的 `/events Read timed out`：说明 server 写路径或请求处理超过 dispatcher 10 秒预算；这既可能是实际未写入，也可能是已写入但响应丢失，必须按幂等重试设计处理。

## 3. 目标

1. 对所有 worker 输出建立可靠事件链：raw stream、projected message/tool/session、final assistant、terminal status 不得静默丢失。
2. server 写侧在可预期并发下不应让 event append、claim、heartbeat 互相拖垮。
3. dispatcher 在 server 背压时有明确 backpressure、retry、diagnostic 与 terminal 屏障策略。
4. UI Conversation/Output 必须基于 cursor 正确追完整事件，不因分页、terminal status 或固定轮询上限漏掉 final。
5. worker driver 与 branch session 语义明确：`branch_continue` 继续 fork branch 的最新 session，不误恢复 source session。
6. 删除或降级 UI 端 backend-specific stdout JSONL parser；Conversation 主路径只消费标准 `ExecutionEvent` 语义事件。

## 4. 非目标

- 不恢复 `/questions`、`/runs/*/transcript`、`run_provenance` 或 server-side backend transcript parser 为主链路。
- 不在本 spec 里设计 WebSocket/SSE 首版强依赖；cursor polling 可继续作为实时机制，但必须正确。
- 不承诺旧 DB/API 的长期兼容。
- 不把所有 worker 输出都拆成细粒度 Fact；raw 证据仍应留在 events/artifacts。
- 不以单纯增大 HTTP timeout 作为验收修复。

## 5. 用户流程

### 5.1 Running Output

1. Worker 产生 stdout/stderr 或 structured message。
2. Dispatcher 将 raw stream 与标准 projected events 写入 durable event channel。
3. UI 以 cursor 增量读取并显示。
4. 若 server 暂时背压，UI 显示最近已落库内容，dispatcher 继续 retry；不得悄悄丢尾部。

### 5.2 Fork / Resume Conversation

1. 用户从 source execution/fact/intent 创建 fork 或 resume branch。
2. Server 创建 question execution 并写 user message event。
3. Dispatcher 根据 `session_action` 和 branch 最新 successful `remote_session_out` 执行 worker。
4. Worker stream、session event、assistant final、terminal status 按顺序进入 `ExecutionEvent`。
5. UI 持续 poll 至 execution terminal 且 final events 已可见；长于 180 秒的回复不得静默停止。

### 5.3 Backpressure / Failure

1. `/events` append timeout 或 5xx 时，dispatcher 保留 batch 并按明确策略 retry。
2. 若同 batch 其实已被 server 写入，event_key 幂等保证重试不重复。
3. 若持续失败超过策略上限，execution 必须暴露 `event_flush_failed` 或等价 diagnostic，不得成功静默结束。
4. Heartbeat 不应因 event flush 背压被轻易饿死；若 worker 被取消，必须有可见原因。

## 6. 功能需求

### 6.1 Dispatcher Event Sink

- Event sink 必须定义 queue 上限、retry 间隔、失败计数、close 最大等待时间和可见 diagnostic。
- Event sink 不得无限内存积压；到达上限时必须采用明确策略：阻塞 reader、落盘 spool、压缩 raw stream，或 fail execution，但不得静默丢语义事件。
- Event sink close 必须形成 terminal 屏障：final message、session event、terminal status event 写入成功后，才能 patch execution terminal status。
- 若 terminal 屏障失败，execution 不得被标记为 `succeeded`；应保留 running/failed-with-diagnostic，或通过原子 finish API 整体失败并可重试。
- Direct final assistant append 不得绕过 EventSink 可靠性。优先由 projector close 产出 canonical final；fallback final 必须在 sink drain 后追加，并检查 `ok`。

### 6.2 Server Event Append

- `event_key` 必须定义为 immutable idempotency key。
- 同 execution 同 event_key 同 canonical event 重试时返回旧 event。
- 同 execution 同 event_key 但 event_type/role/payload/ts 不同，必须返回 409，不得静默吞掉新内容。
- execution events endpoint 的 `after_cursor` 必须属于同 execution；branch timeline 的 `after_cursor` 必须属于同 branch。跨 scope cursor 返回 400。
- server 写路径必须设置 SQLite busy timeout 或等价 retry 策略，避免短暂写锁直接拖垮 dispatcher。
- append batch 应有合理大小上限，事务保持短小；claim、heartbeat、event append 不应共享长事务。

### 6.3 Dispatcher / Server Finish Contract

- 应新增或等价实现 `finish_execution(events, patch)` 原子语义：terminal events 与 terminal patch 在同一 server 事务中完成。
- 若不新增 API，也必须保证 dispatcher patch terminal 前能证明 terminal events 已持久化。
- terminal patch 响应不得成为 UI 停止追 final events 的唯一信号；final event completeness 必须可判定。

### 6.4 UI Conversation / Output Projection

- Conversation 初载不得只取头页；必须 exhaust cursor、支持 tail query，或调用 server-side projection endpoint 返回最新完整 conversation view。
- Running poll 必须持续到 execution terminal，并确认事件 cursor 已追到 terminal status/final assistant；不得固定 180 秒后静默停止。
- 若用户离开再回来，UI 应可从 persisted cursor 或重新分页恢复完整 conversation。
- Raw stdout/stderr 只进入 Raw view；Conversation 主视图只消费标准 `message/tool/session/status` events。
- streaming partial 使用 stable `stream_key` 合并；final assistant 使用同一 stream_key 覆盖 running partial。
- terminal status 不得覆盖或隐藏未完成的 assistant final。

### 6.5 Worker Driver / SSH / Branch Semantics

- `branch_continue` 必须明确定义为继续该 branch 最新 successful execution 的 `remote_session_out`；不等同于恢复 source branch。
- Driver contract 不应只用 `mode="resume"` 表达所有继续语义；必须保留 `session_action` 或 `session_effect`，避免 adapter 误实现。
- SSH stream 实时边界必须明确。若 worker 输出可能无换行，runner/reader 应支持字节或 chunk 级刷新，或在 UI 明示行缓冲限制。
- timeout/cancel 后应验证远端 process group 已终止；若发现远端仍运行，写 system diagnostic event 并反映到 `error_detail`。

### 6.6 Observability

- dispatcher 日志需区分：append timeout、idempotent replay、payload conflict、queue full、terminal barrier failed、heartbeat delayed。
- execution event 中应出现必要 system diagnostic，让 UI 和测试可见。
- 对 event flush 的关键指标至少包括：queue length、oldest queued age、failed_flushes、last_successful_flush_at。

## 7. 数据/API/界面需求

### 7.1 API

保留现有 API：

```http
GET  /projects/{project_id}/executions/{execution_id}/events?after_cursor=...
GET  /projects/{project_id}/branches/{branch_id}/timeline?after_cursor=...
POST /dispatcher/executions/{execution_id}/events
PATCH /dispatcher/executions/{execution_id}
```

新增或等价实现：

```http
POST /dispatcher/executions/{execution_id}/finish
```

语义：

- 请求体包含 terminal events 与 execution patch。
- server 在一个事务内 append events 并 patch terminal status。
- 若任一 event_key 冲突或 payload 不一致，整体失败。

### 7.2 UI

- Conversation 主视图应显示完整 semantic timeline，而非 raw JSONL parser 的二次投影。
- Output/Raw view 可显示 stdout/stderr，并可标注 truncation/omitted range。
- 长时间运行时，若轮询被用户或网络中断，界面应显示可恢复状态，不得表现为自然完成。

## 8. 关键决策点

1. EventSink 背压策略采用哪一种：bounded memory + blocking、bounded memory + disk spool、还是 fail-fast diagnostic？
2. 是否新增 `finish_execution` API，还是在现有 append + patch 上实现可证明屏障？
3. Conversation 完整读取采用 client exhaust cursor、server projection endpoint，还是 tail-first API？
4. Raw stdout JSONL parser 是完全删除，还是仅保留在 Raw/Debug view 中？
5. SSH 实时流是否要从 `readline()` 改为 chunk/byte reader？

## 9. Proposed Architecture Delta

当前 SSOT 事实：

- `ExecutionEvent` 是实时 Output/Conversation 唯一主源。
- Dispatcher 写 events，patch terminal execution status。
- UI 从 execution/branch events 投影实时视图。

目标事实：

- `ExecutionEvent` 主链路增加可靠性边界：dispatcher event flush、server append、terminal patch、UI cursor projection 必须构成可恢复链路。
- Terminal execution status 不再只是独立 patch；它必须与 terminal events 形成持久化屏障，或通过原子 finish contract 提交。
- UI Conversation 主路径不再解析 backend-specific stdout JSONL；raw stream 只作为 raw/debug 证据。
- Cursor scope 从“project cursor 可用于 execution endpoint”收紧为 endpoint-specific scope，避免跨 execution/branch 跳读。

受影响 SSOT 章节：

- `3. 运行层主链路`
- `4. Conversation 与 Session`
- `5. Dispatcher / Server / Driver 边界`
- `7. UI 投影规则`
- `9. 架构变更流程`

行为不变项：

- `ExecutionEvent` 仍为唯一实时主源。
- `Fact/Intent` 仍不承载 runtime state。
- 不恢复旧 `/questions`、`/runs/*/transcript`、`run_provenance`。

迁移/清理范围：

- 清理 UI Conversation 的 backend-specific JSONL parser 主路径。
- 补充 event_key conflict、cursor scope、terminal barrier 的 server/dispatcher tests。
- 若新增 finish API，更新 dispatcher terminal close 调用路径与 SSOT。

何时成为当前事实：

- 对应实现、测试、真实 SSH/Pi E2E 验收通过后，将本 delta 合并进 SSOT 主体，并移除 Pending 标记。

## 10. 验收标准

### 10.1 单元/API

1. 同 event_key 同 canonical event 重试返回旧 event，不消耗 cursor。
2. 同 event_key 不同 payload/type/role/ts 返回 409，不消耗 cursor。
3. execution endpoint 使用其他 execution 的 cursor 返回 400。
4. branch timeline 使用不属于该 branch 的 cursor 返回 400。
5. terminal finish 保证 final assistant/session/status events 与 execution terminal patch 原子成功或整体失败。
6. SQLite 写锁/慢写模拟下，server 不应让普通 event append、claim、heartbeat 大面积超过 dispatcher timeout。

### 10.2 Dispatcher

1. `/events` 首次 read timeout 但 server 已写入时，重试不重复，最终事件完整。
2. `/events` 连续失败时，queue 不无限增长，execution 出现可见 diagnostic。
3. final assistant append timeout 不得静默丢消息。
4. event flush 慢于 20 秒时，heartbeat 不应在合理 grace 内误杀 worker。
5. `close()` 不得在 terminal events 未可靠落库时把 execution 标记为 succeeded。

### 10.3 UI

1. 250+ events 的 execution，final assistant 与 terminal status 仍显示。
2. question 运行超过 180 秒仍持续显示或明确显示“仍在运行/可恢复”，不得静默停止。
3. running partial 被 final assistant 覆盖，不重复、不半截。
4. Raw stdout JSONL 不再作为 Conversation 主路径语义来源。
5. 刷新页面后，Conversation 可恢复完整 timeline。

### 10.4 SSH / Pi E2E

1. Pi fork 首轮长回复完整显示最终回答。
2. Pi fork 后第二轮 `branch_continue` 使用 fork branch 最新 session，而不是 source session。
3. 真实 SSH 环境中长输出、工具输出、final message、session id、terminal status 均可追溯到 execution events。
4. cancel/timeout 后远端进程组被确认终止；若未终止，有 system diagnostic。

## 11. 待确认问题

1. 本轮实现是否接受新增 `POST /dispatcher/executions/{execution_id}/finish`？
2. EventSink 背压优先选择阻塞 reader 还是落盘 spool？
3. Conversation 完整读取是先用 client exhaust cursor 快速修复，还是直接做 server projection endpoint？
4. SSH chunk streaming 是否纳入本轮，还是先作为已知限制并加 diagnostic？
