# V3.5 Agent Context Requirements

日期：2026-05-21
状态：需求草案
依据：用户确认“AGENTS.md 不常变、需要跨 project 复用、创建 project 前选择常用 prompt 并微调”；本轮读取 `docs/architecture/cairn-architecture-ssot.md`、`cairn/tests/e2e_test.md`、`cairn/src/cairn/server/schema.py`、`cairn/src/cairn/server/db.py`、`cairn/src/cairn/server/models.py`、`cairn/src/cairn/server/routers/projects.py`、`cairn/src/cairn/dispatcher/config.py`、`cairn/src/cairn/dispatcher/workers/adapters/pi.py`、`cairn/src/cairn/dispatcher/runtime/environments/{base,docker,ssh}.py`、`cairn/src/cairn/server/static/index.html`、`docs/specs/v1-worker-environment-requirements.md`。

## 1. 核心判断

V3.5 应引入 `agent_context_*` 概念，但 MVP 只支持生成 `AGENTS.md`。

最小正确分层：

- `agent_context_templates` 是 server-wide 可复用模板库，保存在当前 server DB 中。
- project 创建时从模板复制出 project-scoped snapshot，用户可微调；执行以 snapshot 为准，不随模板后续修改漂移。
- dispatcher 在准备 workspace 后 materialize snapshot 到 `AGENTS.md`；worker driver 只负责开启/关闭对应 backend 的 context file capability。

这不是“project 级 DB”。当前 DB 由 `cairn serve --db-path ...` 选择，是 server-wide SQLite；project-scoped setting 是该 DB 中按 `project_id` 关联的行级配置。

## 2. 背景与现状

当前事实：

- server DB 已持久化 `projects`、`facts`、`intents`、`execution_runs`、`execution_events`、environment 与 endpoint 等核心数据。
- `projects` 已有行级设置，如 `auto_reason`、`allowed_auto_workers_json`、`environment_id`。
- worker/model/endpoint 分层来自 v1.1：server 管 environment/provider endpoint；dispatcher 管 workers/model_profiles/调度策略。
- Pi driver 当前固定传入 `--no-context-files`、`--no-extensions`、`--no-skills`、`--no-prompt-templates`，因此不会读取 workspace `AGENTS.md`。
- dispatcher environment 已有 `write_text_file` 与 workspace 边界检查，可在 Docker/SSH workspace 内写受控文件。

用户需求：

- AGENTS.md 内容不频繁变化。
- 常用 agent prompt 需要跨 project 复用。
- 创建 project 前可选择已有模板。
- 创建时可做轻微微调。
- 运行和复盘时应知道该 project 实际使用了哪份内容。

## 3. 目标

- 提供 server-wide agent context template 管理能力。
- 创建 project 时允许选择一个 template，并复制为 project snapshot。
- 允许 project snapshot 后续编辑、启用、停用。
- dispatcher 对启用 snapshot 的 project 写入 workspace `AGENTS.md`。
- Pi worker 在启用 snapshot 时读取 context files；未启用时保持当前隔离行为。
- execution 记录当次使用的 agent context 元数据，至少包括 kind、template id、content hash、materialized path。

## 4. 非目标

- MVP 不支持 MCP、extensions、skills、prompt templates、SYSTEM.md、APPEND_SYSTEM.md。
- MVP 不实现按 model、worker、endpoint 条件注入不同 AGENTS.md。
- MVP 不支持同一 project workspace 中并发 worker 使用不同 AGENTS.md。
- MVP 不把模板放入 dispatcher YAML 作为 source of truth；dispatcher config 最多可作为未来导入/seed 来源。
- MVP 不尝试恢复或解析 worker 私有上下文加载日志。

## 5. 用户流程

1. 用户在 Settings 或 Agent Context 页面创建常用模板，内容类型为 `agents_md`。
2. 用户创建 project 时选择模板，可在创建表单内编辑即将复制的内容。
3. 创建 project 后，server 保存一份 project snapshot。
4. 用户可在 project settings 中查看、编辑、启用或停用该 snapshot。
5. dispatcher 执行任务时读取 project snapshot，写入 workspace `AGENTS.md`。
6. Pi worker 启用 context files 后读取该 `AGENTS.md`，其余 prompt 与 session 机制保持不变。
7. execution metadata 记录本次 materialized context 信息，方便调试和复盘。

## 6. 功能需求

- 模板必须支持 CRUD：
  - `name`
  - `description`
  - `kind = agents_md`
  - `content`
  - `created_at`
  - `updated_at`
  - `content_hash`
- Project snapshot 必须支持：
  - `project_id`
  - `kind = agents_md`
  - `enabled`
  - `source_template_id`
  - `source_template_hash`
  - `content`
  - `content_hash`
  - `created_at`
  - `updated_at`
- 创建 project 时：
  - 可不选择模板。
  - 可选择模板并复制内容。
  - 可在复制前微调内容。
  - 若未选择模板但填写自定义内容，也可创建 snapshot。
- 更新模板不得自动改写既有 project snapshot。
- 更新 project snapshot 不得自动改写源模板，除非未来显式提供“保存为模板”动作；MVP 不做该动作。
- dispatcher materialize 必须是幂等的：同一 content hash 重复写入结果一致。
- 未启用 snapshot 的 project 不应留下 Cairn-managed stale `AGENTS.md`；若 workspace 中的 `AGENTS.md` 被 Cairn ownership manifest 证明为上次 materialize 的内容，则 dispatcher 应清理该文件与 manifest。若无法证明 ownership，则不得删除或覆盖。
- 启用 snapshot 的 project 写入 workspace 根目录 `AGENTS.md`，Pi 不再传 `--no-context-files`。
- Project snapshot 更新后，下一次 materialize 应能覆盖上一版 Cairn-managed `AGENTS.md`；不得把自己上次写入的旧 hash 误判为 unmanaged conflict。
- Agent context content 不应无限大；MVP 建议限制单份 content 不超过 128 KiB，避免 project list、run log、LLM context 和浏览器编辑器被大 prompt 拖垮。

## 7. 数据/API/界面需求

### 数据

新增表：

```text
agent_context_templates
project_agent_contexts
```

`agent_context_templates` 是 server-wide。`project_agent_contexts` 是 project-scoped snapshot。

`execution_runs.metadata_json` 可记录当次上下文元数据；无需新增 execution 核心列，避免为非主链路事实膨胀 schema。该 metadata 必须进入 execution ledger，可经 execution API 复盘；仅写入 run log metadata 不满足要求。

### API

新增或扩展 API：

- `GET /agent-context/templates`
- `POST /agent-context/templates`
- `GET /agent-context/templates/{template_id}`
- `PATCH /agent-context/templates/{template_id}`
- `DELETE /agent-context/templates/{template_id}`
- `GET /projects/{project_id}/agent-context`
- `PUT /projects/{project_id}/agent-context`
- `POST /projects` 接收可选 `agent_context` payload。

Dispatcher 需要只读 endpoint：

- `GET /projects`、`GET /projects/{project_id}`、`GET /projects/{project_id}/graph` 只返回 agent context summary，不包含 full content。
- `GET /projects/{project_id}/agent-context` 返回 full snapshot content，供 UI editor 与 dispatcher 使用。

必须避免 dispatcher 直接读 DB。

### 界面

UI 至少支持：

- 模板列表、创建、编辑、删除。
- 创建 project 时选择模板，并展示可编辑内容。
- Project settings 中查看、编辑、启用、停用 snapshot。
- 展示 snapshot 是否来自某模板及 hash/更新时间。

## 8. 关键决策点

- 模板引用与 snapshot：采用“创建时复制”，而不是运行时引用模板。
- Source of truth：server DB，而非 dispatcher config。
- Driver 边界：Driver 不生成、不读取 DB、不决定内容；只根据 resolved runtime context 控制 CLI 参数。
- 既有 workspace `AGENTS.md` 冲突：MVP 应拒绝静默覆盖 unmanaged 文件，并把冲突作为 execution diagnostic；但 Cairn 应用 sidecar manifest 识别并覆盖/清理自己管理的旧文件。
- Scope 命名：表/API 使用 `agent_context`，但 MVP `kind` 只允许 `agents_md`。

## 9. Proposed Architecture Delta

当前 SSOT 事实：

- Server 持久化 projects、facts、intents、executions、events、branches、artifacts、environment config。
- Dispatcher 选择 worker driver 与 environment，启动 worker process。
- Worker driver 将具体 CLI/API 输出转成统一 execution events，并实现 session 语义。

目标事实：

- Server 还持久化 agent context template 与 project agent context snapshot。
- Dispatcher 在 worker process 启动前，从 server 获取 project agent context snapshot，并在 workspace 内 materialize backend-readable context files。
- Worker driver 暴露 backend capability 开关，例如 Pi context files，但不拥有 agent context 内容来源。
- Execution metadata 记录本次 materialized agent context 的 kind、hash、path 与启用状态。

受影响 SSOT 章节：

- `5. Dispatcher / Server / Driver 边界`
- `9. 架构变更流程`

行为不变项：

- Output/Conversation 主链路仍是 `ExecutionRun -> ExecutionEvent`。
- Fact/Intent/Execution/Branch/Artifact 边界不变。
- Provider endpoint 与 model_profile 分层不变。
- 不恢复 `/runs/*/transcript`、`/questions`、`run_provenance`。

迁移/清理范围：

- Fresh schema 与 migration 需新增 agent context 表。
- Pi driver 中 `--no-context-files` 从固定参数变为按 runtime context 决定。
- 不清理 `--no-extensions`、`--no-skills`、`--no-prompt-templates`；它们仍保持默认关闭。

Delta 成为 current 的条件：

- schema/API/UI/dispatcher/Pi driver 实现完成。
- 测试覆盖 migration、template CRUD、project snapshot、dispatcher materialize、Pi argv 开关。
- 按 `cairn/tests/e2e_test.md` 手动模拟完整操作流程；除测试环境不可解问题外，不得跳过 E2E。
- SSOT 主体合并上述目标事实，并移除 Pending marker。

## 10. 验收标准

- 用户能创建一个 agent context template。
- 用户能在创建 project 时选择模板并微调。
- 创建后修改模板不影响该 project snapshot。
- 用户能在 project settings 中编辑、启用、停用 snapshot。
- 启用 snapshot 的 project 执行 Pi worker 时，workspace 根目录出现 `AGENTS.md`，Pi 命令不含 `--no-context-files`。
- 未启用 snapshot 的 project 执行 Pi worker 时，Pi 命令仍含 `--no-context-files`。
- 发生既有 unmanaged `AGENTS.md` 冲突时，不静默覆盖，execution 通过标准 finish contract 失败并输出明确 diagnostic。
- 用户编辑 project snapshot 后再次执行，workspace 中上一版 Cairn-managed `AGENTS.md` 被正常更新，不误报冲突。
- 用户停用 project snapshot 后再次执行，上一版 Cairn-managed `AGENTS.md` 被清理，Pi 命令恢复包含 `--no-context-files`。
- execution metadata 能显示本次 agent context 的 content hash 与 materialized path。
- 现有 Output/Conversation、fork/resume、environment/endpoint 流程不回归。
- E2E 验收必须覆盖较长流式输出能否完整同步、正确显示，并在测试后关闭测试用监听服务。

## 11. 待确认问题

- 删除 template 时，是否允许删除仍被 project snapshot 标记为 source 的模板？建议允许，因为 snapshot 已复制；UI 仅显示 source missing。
- Project snapshot 空内容且 enabled=true 时是否允许？建议不允许，避免“启用但无效果”。
- 首版是否需要内置一个默认模板？建议不内置，避免把个人偏好写进产品默认行为。
