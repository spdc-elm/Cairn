结论先行：server 管任务、地点与 endpoint，dispatcher 管兵力与模型

v1.1 的修正是承认 base_url 与 api_key 通常同属一个 provider endpoint。地点与 endpoint 由 Web UI 与 server 管理，模型与 worker fleet 由 dispatcher 配置管理。

server.db

保存 project、environment、project-environment binding、provider endpoint、healthcheck。

dispatcher config

保存 runtime、worker 列表、model profile、调度策略。

一句话：project 绑定执行地点，environment endpoint 决定从哪里调 provider，worker/model_profile 决定用什么模型。

v0 已证明 SSH backend 可行

这一轮不是纸面设计。v0 已经完成一条真实路径：dispatcher 通过 server 配置的 SSH environment 拉起远端 Pi agent worker。

抽象已落地

任务层从 ContainerManager 解耦到 WorkEnvironment，Docker 成为 backend adapter。

SSH runner 已跑通

支持 workspace prepare、远端 runner、stdout/stderr、timeout、cancel、cleanup。

Web UI 已具雏形

可创建 environment，触发 healthcheck，创建 project 时选择 execution environment。

dispatcher 可选地点

按 project.environment_id 选择 backend，worker selection 可按 allowed_environments 过滤。

Pi harness 可运行

在远端 workspace 写私有 .cairn/pi/<worker> 配置并执行 Pi agent。

核心遗留问题

server environment 混入 pi_model、base_url、api_key、provider_api，边界开始模糊。

职责边界：把“地点”和“能力”拆开

导师评审重点：这不是文件摆放问题，而是系统真相源划分。server 不应知道用什么 LLM 完成任务。

v0 混叠
  • environment 同时保存 SSH 地点与 Pi provider。
  • server 需要知道模型 endpoint 与 key。
  • healthcheck 归因混乱：地点失败与模型失败混在一起。
  • snapshot 与兼容逻辑制造多个 truth source。
v1 收口
  • environment 描述执行地点与该地点的 provider endpoint。
  • model_profile 只描述模型与上下文能力。
  • server API redacted 返回 endpoint，dispatcher healthcheck 测完整 worker matrix。
  • project 只持久化 environment_id。

两个删除决定：不做 snapshot，不做兼容

此处是 v1 的设计取舍。现在系统未到稳定 MVP，保留临时兼容会把错误抽象固化。

不做 snapshot

  • MVP 主目标是调度与执行，不是审计复现。
  • snapshot 会制造第二个 environment truth source。
  • 执行真相唯一：project.environment_id 指向当前 server environment。

不做兼容

  • v0 还未成为产品契约。
  • 旧 container.* 与 server-side pi_* 会持续污染边界。
  • 允许 docker-default，但它只是地点 backend。
若以后需要审计，再新增只含非敏感地点信息的历史记录，且不得作为调度输入。

调度链路：Web UI 改地点，dispatcher 不重启也能用

新增需求的关键是 environment registry 热刷新。server-side environment 是用户操作面，不应要求重启 dispatcher 才生效。

1. 读配置dispatcher 解析 runtime、workers、model_profiles。配置文件显式选择 dev/local。
2. 拉地点定期从 server 拉 environments 与 redacted endpoints。
3. 校验矩阵allowed_environments 与 worker.endpoint 必须存在。
4. 选择 workerproject.environment_id 过滤 worker fleet。
5. 执行任务model_profile + server endpoint 解析 Pi 所需 env。

风险审计：v1 可行，但要盯住四个边界

这些不是反对 v1，而是实现时最容易走偏的地方。展开可见对应控制策略。

不能只在 YAML 加载时校验，因为 environment 由 server 管。应在拉取 server environments 后统一校验，并允许热刷新后更新矩阵。
server 测地点与 endpoint 配置；dispatcher 测 worker + model_profile + endpoint + environment。模型失败不应污染单纯地点健康状态。
server DB 可保存 key，但 API/UI 默认 redacted；run log、request.json、静态 HTML 与 project metadata 不得出现明文 key。
修改只影响新任务；运行中任务继续使用已创建 handle。删除 environment 后不回退默认地点。

验收口径：用测试压住边界

v1 的质量标准不是“SSH 能跑一次”，而是职责边界、热刷新、secret 安全、UI 可解释全部成立。

DB 收口

server DB 不新增或展示任何 LLM key/provider 字段。

绑定唯一

创建 project 后只持久化 environment_id。

地点可管

Environment 面板可创建 SSH 地点并触发地点 healthcheck。

热刷新

Web UI 新增或修改 environment 后，dispatcher 无需重启即可用于后续调度。

路径可见

Project detail 顶栏显示 environment 与 workspace 路径。

安全闭环

run log 不包含 API key 明文。

导师要拍板的问题：v1 是否接受“破坏式收口”，以及是否同意把 server-side model credential 全部移出 environment。
