Cairn Worker Environment SSH-First 重构计划 v0

历史版本：已被 docs/specs/v1-worker-environment-requirements.md 取代。v1 明确 server 管任务与地点，dispatcher 管兵力与凭据；不做 snapshot，不兼容 v0 临时 schema。

版本：v0 / superseded 日期：2026-05-18 现状依据：当前 project 表无 environment 字段 主 backend：ssh 兼容 backend：docker

一、判断

结论：你的方向是对的。Cairn 真正需要的是“远程工作环境”，不是“Docker 容器”。Docker daemon 远程控制虽省代码，但安全边界过大；SSH 更接近 VS Code Remote 的心智模型，也更适合让用户决定远端到底是裸机、虚拟机、容器、tmux 会话，还是已准备好的安全工具环境。

故重构的核心不是把 Docker API 换成 SSH 命令，而是把当前 ContainerManager 抽象为 WorkEnvironment：它能写文件、执行命令、回读输出、取消进程、保留或清理现场。Docker 只是该接口的一个实现。

二、第一性原理

Cairn 的 worker 环境本质要解决四件事：

一阶需求 解释 SSH-first 下的设计
可抵达 dispatcher 能免交互连接远端，不被密码、host key、网络阻塞。 ssh -o BatchMode=yes、known_hosts 检查、SFTP 写入测试。
可运行 远端有 agent harness 与基础命令。 先以 pi 为主，检查 pi、python3、timeout、setsid、workspace 权限。
可观测 worker 输出必须实时回流，后续 UI 才能增强交互感。 SSH channel 读 stdout/stderr；run log 保持 JSONL；后续可接 tmux/zellij capture-pane。
可收束 任务超时、project stopped、heartbeat 丢失时，远程进程不能残留。 远端 runner 以 process group 启动任务，取消时 kill 整组。

关键边界：SSH backend 不提供 Docker 的镜像复现与 namespace 隔离。它应声明为“可信远程环境”，由用户保证环境内容；Cairn 负责调度、注入、执行、回读与清理。

三、目标体验

登记环境用户或配置声明远程机、用户、workspace、harness 类型。
健康检查检查 SSH 免密、远端命令、workspace、pi agent、可选模型调用。
创建项目New Project 时选择一个 work environment。
调度执行dispatcher 在该环境中运行 bootstrap/reason/explore。
保留现场项目 stop/completed 时按策略保留 workspace、tmux/zellij 会话或清理。

理想 UI 不是“选 Docker 容器”，而是选：

mac-mini-local
kali-vm-ssh
ctf-box-ssh-container
gpu-worker-ssh
legacy-docker-local

至于这些环境内部是否 Docker，由用户自己决定。若用户要“SSH 进容器”，只需把 SSH server 放在容器里，Cairn 仍只看见一个 SSH endpoint。

四、数据模型与配置

1. Project 绑定环境

当前 projects 表无环境字段；需增加：

ALTER TABLE projects ADD COLUMN environment_id TEXT;
ALTER TABLE projects ADD COLUMN environment_snapshot_json TEXT;

environment_id 用于调度；environment_snapshot_json 用于审计与 UI 展示，避免配置后来改名或删除后项目失去历史上下文。

2. 环境目录

建议新增一个 redacted-first 的环境配置文件，server 和 dispatcher 都能读取，但 secret 只以引用形式出现。

environments:
  - id: kali-vm
    label: "Kali VM"
    backend: ssh
    host: "192.168.56.10"
    port: 22
    user: "kali"
    auth:
      mode: agent
    workspace_root: "/home/kali/cairn-workspaces"
    harness: pi
    terminal:
      mode: none        # none | tmux | zellij
    cleanup:
      completed: keep   # keep | stop | remove
      stopped: stop
    credentials:
      mode: remote      # remote | inject | merge

  - id: docker-local
    label: "Local Docker"
    backend: docker
    image: "ghcr.io/oritera/cairn-worker-container:latest"
    network_mode: host
    completed_action: stop
    credentials:
      mode: inject

3. Worker 与环境分离

保留当前 workers[] 的“LLM 并发配额单元”意义，但把执行地点从 worker 中拆走：

workers:
  - name: pi-main
    type: pi
    task_types: [bootstrap, reason, explore]
    max_running: 2
    priority: 0
    allowed_environments: ["kali-vm", "docker-local"]
    env:
      PI_MODEL: "..."
      PI_BASE_URL: "..."
      PI_API_KEY: "${CAIRN_PI_API_KEY}"
      PI_PROVIDER_API: "openai-completions"

当 credentials.mode=remote 时，worker env 中可不填 baseurl/key，driver 需走远端已有 pi 配置；当 inject 时才按当前逻辑注入。

五、SSH Health Check

health check 分层，失败信息要能在 UI 直接显示。

层 检查项 失败含义
连接层 ssh -o BatchMode=yes -o ConnectTimeout=5 user@host true 无免密、公钥未装、host key 未确认、网络不可达。
文件层 SFTP 创建 $workspace_root/.cairn-healthcheck，写读删。 workspace 不可写，权限或磁盘有问题。
harness 层 command -v pi、pi --version、python3 --version、timeout --version、setsid --version。 远端不是合格 worker runtime。
模型层 若 credentials.mode=inject，用注入 env 跑 pi ping；若 remote，用远端已有配置跑 pi ping。 模型配置、baseurl、key 或 provider 不可用。
回读层 运行一个产生 stdout/stderr 的短命令，确认 dispatcher 分流记录。 UI 后续实时输出不可靠。

startup healthcheck 应从“新建 Docker 容器检查所有 worker”改为“检查所有 environment + worker 组合”。项目调度前仍可做轻量 worker healthcheck，但不应每次都重测 SSH 免密。

六、执行与输出回读

1. WorkEnvironment 接口

class WorkEnvironment(Protocol):
    def id(self) -> str: ...
    def prepare_project(self, project_id: str) -> EnvironmentHandle: ...
    def write_text_file(self, handle: EnvironmentHandle, path: str, content: str) -> None: ...
    def build_process(
        self,
        handle: EnvironmentHandle,
        env: dict[str, str],
        command: list[str],
        timeout_seconds: int | None,
        run_logger: RunLogWriter | None,
    ) -> ManagedProcessLike: ...
    def inspect(self, handle: EnvironmentHandle) -> EnvironmentState: ...
    def cleanup(self, handle: EnvironmentHandle, reason: str) -> CleanupResult: ...

2. SSH 远端 runner

不要把复杂命令直接拼成一整段 shell。应在远端 workspace 下放一个小 runner，输入为 JSON，负责 env、cwd、process group、timeout、stdout/stderr framing。

~/.cairn/bin/cairn-runner execute \
  --workspace /home/kali/cairn-workspaces/p12 \
  --request /home/kali/cairn-workspaces/p12/.cairn/run-abc/request.json

请求文件示意：

{
  "argv": ["pi", "--provider", "cairn", "--model", "model-name", "-p", "prompt"],
  "env": {"PI_API_KEY": "..."},
  "timeout_seconds": 300,
  "kill_after_seconds": 5,
  "session": {"terminal": "none"}
}

runner 启动时用 setsid 建独立进程组；取消时 dispatcher 调用 cairn-runner cancel --run-id ...，由远端 kill 进程组。

3. tmux / zellij 路线

第一版先做 raw SSH channel，保证输出能进现有 run log。第二版可加 terminal backend：

terminal:
  mode: zellij
  session_template: "cairn-{project_id}"
  pane_per_task: true
  capture_interval_ms: 500

这会带来更强的 UI 交互感：用户可看到 worker 真实终端、可 attach、可回放 pane 内容。但不宜放在第一版，否则进程控制和输出语义会过早复杂化。

七、凭据注入策略

这是必须显式配置的边界，不应隐式猜。

模式 含义 适用场景 注意
remote 远端已配置 baseurl/key，dispatcher 不传 secret。 用户维护自己的 VM / 容器；安全边界最好。 healthcheck 必须能验证远端配置真的可用。
inject dispatcher 将 worker env 注入远端进程。 集中管理模型 key；远端只是算力和工具环境。 secret 不可进 argv、日志、request.json 明文长期留存。
merge 远端保留默认配置，dispatcher 只覆盖指定变量。 临时切换模型或 endpoint。 需记录 effective config 的 redacted 摘要，便于复盘。

当前 Pi driver 会把模型配置写成 models.json，其中可能含 key。SSH 版若采用 inject，需把该文件放在 run 私有目录，任务结束按策略删除；若采用 remote，driver 应允许跳过生成 models.json，直接使用远端已有 harness 配置。

八、原 Docker 元能力对齐

现有 Docker 能力 SSH-first 对应 是否可达成
创建 worker 容器 创建 project workspace；可选创建 tmux/zellij session。 可达成，但语义从“容器”变为“环境句柄”。
复用项目级状态 同一 project workspace 保存 session、工具输出、临时文件。 可达成。
写入 graph snapshot SFTP 写入 workspace 内受控路径。 可达成。
exec worker 命令 SSH runner 执行 argv。 可达成。
回读 stdout/stderr SSH channel 分流；run log 保持现有 JSONL。 可达成，且是 UI 交互增强基础。
超时 / 取消 远端 process group + runner cancel。 可达成，但必须测试远程残留进程。
stop/remove stop=kill active runs, keep workspace；remove=删 workspace；completed 可配置。 可达成。
镜像隔离 / cap / network namespace 由用户远程环境自行保证。 不等价；必须在 UI/文档中明示。

九、实施计划

  1. 接口抽象。新增 dispatcher/runtime/environments/base.py，定义 WorkEnvironment 与 ManagedProcessLike；把现有 Docker 实现包成 DockerEnvironment，行为不变。
  2. 配置重构。新增 environments[]；旧 container.* 自动迁移为一个 docker-default 环境，保证兼容。
  3. Project schema。给 project 增 environment_id 与 snapshot；CreateProjectRequest 增可选 environment_id；ProjectMeta/Summary/Detail 返回 redacted environment 信息。
  4. UI 选择。New Project modal 加 environment 下拉；project 卡片显示环境 badge；环境不可用时给 warning，不阻塞历史项目查看。
  5. SSH backend MVP。基于本地虚拟机测试：免密连接、workspace prepare、SFTP 写图谱、runner 执行 pi mock、stdout/stderr 回流、取消无残留。
  6. 凭据模式。实现 remote 与 inject；Pi driver 先支持 remote 配置，不强写 models.json。
  7. 终端复用二期。在 SSH backend 下加 tmux/zellij adapter，先只 capture 输出，不直接允许 UI 输入控制。

十、测试矩阵

场景 验收标准
本地 Docker 兼容 旧 dispatch_mock.yaml 可跑；mock project lifecycle 与原行为一致。
SSH 免密失败 healthcheck 明确报 public key / BatchMode 失败，不挂起。
远端缺 pi 环境状态显示 harness missing；dispatcher 不派发。
远端 remote credentials dispatcher 不传 key；远端 pi ping 成功。
远端 inject credentials key 不出现在 argv、run log、UI；任务可调用模型。
任务输出回读 stdout/stderr 实时写入现有 run log；latest run API 可读。
取消与超时 project stopped 后远端无残留 worker 进程。
workspace 保留 completed keep 模式下现场仍在；remove 模式下目录消失。

十一、我建议的第一刀

不要先做 tmux/zellij

先把 SSH runner 的 stdout/stderr、取消、workspace 做稳。终端复用是 UI 增强，不是执行语义的地基。

不要让 server 持有明文 key

server 只需要 environment metadata；secret 留在 dispatcher 环境变量、密钥文件或远端机器。

先以 pi 为唯一 SSH harness

Claude/Codex 后接。先让一个 driver 跑通，避免同时处理三套 session 行为。

保留 Docker backend

不是因为它是理想形态，而是它给回归测试提供稳定参照物。

最终形态：Cairn 调度 project；project 绑定 work environment；work environment 可以是 SSH 远程机、SSH 容器、本地 Docker、远程 Docker。worker driver 只关心如何构造 agent 命令，不再关心命令在哪里运行。
