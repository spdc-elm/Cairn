依据：`docs/specs/v3-interactive-worker-qna-requirements.md`、`docs/plan/v3-interactive-worker-qna-execution-plan.md`、`docs/plan/v3-interactive-worker-qna-architecture-recovery-plan.md`、2026-05-19 未提交实现审计；本文件为 v3.1 修正版，后续实现与验收以本文件为准。

## 0. 总判

当前未提交实现有两类东西：一类是正确底座，一类是赶工漂移。不能全推倒，也不能沿着现状继续补。

保留：

- `run_provenance` 作为 DB source of truth。
- `run_worker_process(...)` 返回 `run_log_id`。
- fact metadata 写入 `provenance.producing_run_log_id`。
- transcript 从完整 outer run JSONL 重建 stdout/stderr，再做 worker-specific normalization。
- Pi 高频 delta coalesce。
- promotion metadata 记录 anchor/source run/mode/session effect。

必须返工：

- server 不能直接连接远端、不能构造 `SshEnvironment`、不能运行 worker process。
- server 不能 import worker driver 来计算 capability。capability 由 dispatcher 发布，server 只读库存。
- Q&A 不能是 HTTP 同步长请求。必须是 server enqueue job，dispatcher claim/run/report，UI poll/SSE 展示状态。
- fork 不能被全局 `false` 固化。v3.1 必须交付真实 backend fork 能力；Mock fork 只用于 contract/UI 测试，不能作为交付验收。默认验收目标是 Pi fork 与 Codex fork 两条真实路径。Claude Code fork 可缓做，不阻塞 v3.1 验收。
- fresh_context 多轮不能只传当前问题。必须有 thread history / summary。
- fork/fresh_context 的“短期不保存”不能靠单进程内存糊弄。跨 server/dispatcher 需要 runtime store，但 close/TTL 后清理，不作为长期历史。
- job protocol 必须有 lease、heartbeat、requeue、幂等 event append、cancel/close 语义。短期态也必须能从 dispatcher crash/server restart 中恢复到确定状态。

本计划的架构铁律：

```text
Server = control plane
Dispatcher = execution plane
Driver = backend command/capability adapter
Environment = remote/local execution substrate
RunProvenance DB = run/session truth
Run JSONL = raw transcript artifact
QuestionRuntime = short-lived interaction state, not historical archive
```

执行顺序红线：

- Phase 0 架构护栏 RED 不写完，不进入 Phase 1。
- 任一 phase 的审查点未通过，不进入下一 phase。
- 若实现中发现 spec 与 repo 事实冲突，先更新 plan 并说明，不得私自改语义。
- 若某 backend fork 未被实测证明，不得在 UI/API 中显示为可用。
- 若 Pi 或 Codex 当前版本无法提供 fork，v3.1 implementation 必须暂停在 fork phase，给出阻断报告或升级要求；不得以 Mock fork、Claude Code fork、resume fallback 宣告 v3.1 完成。Claude Code 当前版本不支持 fork 时，只记录 reason，不阻塞 v3.1。

## 1. 边界契约

### 1.1 Server 只做控制面

允许：

- project/fact/intent/hint CRUD。
- `resolve_anchor`。
- run provenance CRUD/query。
- transcript read/normalization API。
- question thread/job/event runtime state。
- question promotion。
- worker inventory/capability read model。

禁止：

- `cairn.server.*` import `cairn.dispatcher.runtime.environments.*`。
- `cairn.server.*` import `cairn.dispatcher.runtime.process`。
- `cairn.server.*` 调 `run_worker_process(...)`。
- `cairn.server.*` 构造 `WorkerConfig.env` 或读取 endpoint secret 以执行 worker。
- `cairn.server.routers.questions` import `get_driver()`。
- server 因 dispatcher 不在线而 fallback 为直连远端。

允许的例外：

- 纯数据模型可放共享模块，例如 `cairn.shared.question_contracts`。
- transcript parser 若需要跨 server/dispatcher 复用，应放纯解析模块，例如 `cairn.worker_events`，不得 import environment/process/config secret。

### 1.2 Dispatcher 只做执行面

负责：

- 发布 worker inventory 与 question capability。
- claim question job。
- 选择 worker/environment。
- 调 driver `build_question(...)`。
- 调 environment 执行进程。
- 写 run log、run provenance、remote session update。
- 回写 question events/result/error。
- timeout、cancellation、heartbeat、lease、requeue。

禁止：

- 直接改 server DB。
- 绕过 server API 创建 fact/hint/intent。
- 对 fork/fresh_context 写长期 run provenance，除非显式 debug flag；默认只写 short-lived question events。

### 1.3 Driver 只吸收 backend 差异

负责：

- `build_execute(...)`。
- `build_conclude(...)`。
- `build_question(...)`。
- `extract_session_provenance(...)`。
- `question_capability(...)`。
- 注册/暴露 transcript parser 名称或纯解析器。

禁止：

- driver 自行决定 question 是否可创建。创建/锁/TTL 属 server。
- driver 自行写 DB。
- driver 为了统一而伪造 fork。

### 1.4 UI 只表达真实能力

要求：

- `fork` 可用时默认展示 `Ask in Fork`。
- `fork` 不可用时展示原因，而不是静默消失。
- `resume` 必须危险确认，并说明会继续 source remote session。
- `fresh_context` 永远可用，但文案说明它使用摘要，不是原 session。
- running/open intent 不显示 Ask。
- selected/latest run 必须可见；fact 默认 producing run。

## 2. 状态机

### 2.1 QuestionThread

```text
active
  -> closing
  -> closed

active
  -> failed

active
  -> expired
```

规则：

- `active` 可追加 message/job。
- `closing` 拒绝新 message，等待 active job 结束或取消。
- `closed` 删除短期 events/jobs 后保留 tombstone，GET 返回 410。
- `failed` 保留错误到 TTL，允许用户查看并 close。
- `expired` 来自 TTL cleanup 或 server restart recovery，GET 返回 410。

### 2.2 QuestionJob

```text
pending
  -> claimed
  -> running
  -> succeeded

pending/claimed/running
  -> failed

pending/claimed/running
  -> cancelled

claimed/running
  -> pending  (lease expired / dispatcher lost)
```

规则：

- `pending` 由 server 创建。
- `claimed` 必须有 `claimed_by`、`claim_expires_at`。
- `running` 可 append events。
- `succeeded` 必须有 assistant message/result summary。
- `failed` 必须有 `error_code` 与 human-readable `error_detail`。
- `cancelled` 由 close/abort/TTL 触发。
- `claimed/running` lease 过期可 requeue；若 worker process 可能仍在远端执行，dispatcher 必须 best-effort cancel，并把重试策略写入 error/requeue metadata。
- events append 必须幂等：dispatcher 重试同一 batch 不得产生重复 UI event。
- finish/fail 必须幂等：重复上报同一 terminal state 返回当前 job，不二次释放 lock、不二次写 assistant message。
- server startup 时，所有 `claimed/running` 且 lease 过期的 job 标为 `pending` 或 `failed`；首版默认 `pending`，但 `resume` job 默认 `failed_requires_manual_retry`，避免重复污染 source session。

### 2.3 Resume Lock

key：

```text
(project_id, source_remote_session_kind, source_remote_session_id)
```

规则：

- 只锁 `mode=resume`。
- `fork/fresh_context` 不占用 resume lock。
- lock 创建于 thread/job creation 前后同一 DB transaction。
- lock 释放于 job succeeded/failed/cancelled/closed/expired。
- lock 超时必须可恢复，避免 server crash 后永久锁死。

TTL：

- default active TTL: 24h。
- close 后立即删除 events/jobs，并把 thread tombstone 保留 1h。
- expired thread 返回 410。
- server 启动时运行 runtime recovery：过期 thread -> expired；过期 locks -> release；过期 claimed jobs -> requeue/fail by mode。

幂等键：

- user message job: `thread_id + seq`。
- dispatcher event append: `job_id + event_key`；若 adapter 无稳定 event id，则 dispatcher 生成 `batch_id:index`。
- finish/fail: `job_id + terminal_status + run_log_id/result_digest`。

## 5. Prompt Context Contract

### 5.1 Context Builder

新增纯 server service：

```text
build_question_context(conn, thread, message) -> QuestionPromptContext
```

包含：

- project id/title。
- anchor summary。
- source run provenance。
- selected transcript summary。
- report path/reference if available。
- prior question messages。
- mode-specific instruction。

### 5.2 Mode Rules

fork：

- prompt 可短，因为 remote fork 继承 source session。
- 仍附 Cairn anchor/provenance 供 worker理解 UI 语境。
- question session id 必须作为 `question_remote_session` 回写。

resume：

- prompt 明确“continuing source session”。
- 不能自动改黑板。
- 写操作需用户在 message 中明确要求。
- run provenance 必须记录 `session_effect=continued`。

fresh_context：

- 必须包含 anchor summary、report path/report excerpt 或 transcript summary。
- 第二轮起必须包含 prior Q&A messages 或压缩 summary。
- 不得声称连接到原 worker session。

## 8. Phase 2: Dispatcher Question Job Execution

### 目的

让 dispatcher 接管所有 question execution。

### 范围

```text
cairn/src/cairn/dispatcher/protocol/client.py
cairn/src/cairn/dispatcher/scheduler/loop.py
cairn/src/cairn/dispatcher/tasks/questions.py
cairn/src/cairn/dispatcher/tasks/common.py
cairn/src/cairn/dispatcher/workers/base.py
cairn/src/cairn/dispatcher/workers/adapters/*.py
cairn/src/cairn/server/routers/dispatcher_questions.py
```

### 步骤

1. `CairnClient` 增加 dispatcher-facing question endpoints。
2. server router 增加 claim/start/events/heartbeat/finish/fail/requeue/cancelled。
3. scheduler loop 每 tick：

```text
publish_worker_inventory_with_capability()
claim_question_job()
if job:
  run_question_task(job)
```

4. `run_question_task`：

- load project detail。
- prepare environment via existing dispatcher environment registry。
- build prompt from `job.prompt_context` and message。
- call `driver.build_question(...)`。
- call `run_worker_process(...)`。
- parse session provenance。
- parse transcript events from stdout/stderr。
- append events。
- finish/fail job。
- for resume only: create run provenance and update session.
- on cancellation: best-effort cancel process, report `cancelled`, release resume lock.
- on dispatcher crash: rely on claim lease; next dispatcher reclaims only after server recovery/requeue.

5. lease/heartbeat：

- dispatcher heartbeats claimed job。
- server requeues expired claims.
- close/TTL asks dispatcher to cancel active job by making subsequent heartbeat/append return cancellation signal.

6. idempotency：

- every append events request uses deterministic event keys.
- finish/fail are retry-safe.
- run provenance creation for resume uses `run_log_id` primary key and `ON CONFLICT` update, not duplicate insert.


覆盖：

- unavailable worker not claimed。
- dispatcher heartbeat extends lease。
- expired claim requeues。
- duplicate event append stays single。
- duplicate finish/fail does not duplicate assistant message。
- server close causes dispatcher cancellation path。
- fake environment success appends assistant event and marks succeeded。
- fake environment failure marks failed and releases resume lock。
- resume mode creates run provenance with `task_type=question`。
- fork/fresh_context do not create persistent run provenance by default。
