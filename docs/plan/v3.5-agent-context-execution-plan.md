依据：`docs/specs/v3.5-agent-context-requirements.md`、`cairn/tests/e2e_test.md`

## 0. 目标边界

实现 server-managed reusable agent context template 与 project-scoped snapshot，MVP 只 materialize `AGENTS.md`。

核心边界：

- Server 是 template 与 project snapshot 的 source of truth。
- Dispatcher 负责在 workspace 内 materialize snapshot。
- Driver 只负责 backend-specific CLI capability，例如 Pi 是否传 `--no-context-files`。
- Execution 只在 `metadata_json` 记录 agent context hash/path，不新增执行主链路表。
- 不引入 MCP、extensions、skills、prompt templates。
- 不恢复 `run_provenance`、`/runs/*/transcript`、`/questions`、`server/transcripts/*`。

复杂度分级：cross-module-or-protocol，触及 schema/API/UI/dispatcher/driver，但不改变 Output/Conversation 主链路。

SSOT 生命周期：

- 已在 `docs/architecture/cairn-architecture-ssot.md` 增加 Pending marker：`v3.5-agent-context`。
- 实现阶段保留 Pending marker。
- 全部测试与 smoke 验收通过后，把 Server/Dispatcher/Driver 边界的新事实合并进 SSOT 第 5 节，并移除 Pending marker。

## Phase 0: Contract First 与测试基线

### 目的

先固定 API/schema/runtime contract，避免 UI 与 dispatcher 各自猜字段。

### 步骤

1. 阅读并确认当前 migration runner、fresh schema、project create/update API、dispatcher client、Pi driver 参数构造。
2. 新增 server model contract：
   - `AgentContextKind = Literal["agents_md"]`
   - `AgentContextTemplate`
   - `AgentContextTemplateCreate`
   - `AgentContextTemplateUpdate`
   - `ProjectAgentContext`
   - `ProjectAgentContextUpsert`
   - `CreateProjectRequest.agent_context`
   - `ProjectMeta.agent_context_summary`
3. 明确 hash 算法：`sha256(content.encode("utf-8"))`，输出 hex。
4. 明确空值规则：
   - template content 可为空与否需统一；建议不允许空内容。
   - project snapshot `enabled=true` 时 content 必须非空。
   - `agent_context=null` 表示 project 不启用 managed AGENTS.md。
5. 明确 unmanaged workspace conflict 策略：
   - Materializer 必须维护 sidecar ownership manifest，建议路径为 `workspace/.cairn/agent-context/agents_md.manifest.json`。
   - Manifest 至少记录 `kind`、`target_path`、`last_materialized_hash`、`source_template_id`、`updated_at`。
   - 若 `AGENTS.md` 不存在 -> 写入 target 与 manifest。
   - 若 `AGENTS.md` 存在且 hash 等于目标 snapshot hash -> 更新 manifest 并继续。
   - 若 manifest 存在且当前 `AGENTS.md` hash 等于 `last_materialized_hash` -> 视为 Cairn-managed stale file，可覆盖为新 snapshot。
   - 若 manifest 存在但当前 `AGENTS.md` hash 不等于 `last_materialized_hash` -> 视为 workspace 手动修改，conflict。
   - 若 manifest 不存在且 `AGENTS.md` hash 不等于目标 snapshot hash -> unmanaged conflict。
   - 若 snapshot disabled 且 manifest 证明当前 target 是 Cairn-managed -> 删除 `AGENTS.md` 与 manifest；否则不碰 workspace 文件。
6. 明确 execution metadata 规则：
   - Agent context metadata 必须写入 `execution_runs.metadata_json`，可经 execution API 读回。
   - `run_worker_process(extra_metadata=...)` 只作为 run log 补充，不得被当成 ledger metadata。
   - 若需要 patch metadata，必须 merge 既有 metadata，避免覆盖 task/session 其它字段。
7. 明确 content 暴露与大小限制：
   - content 最大 128 KiB。
   - Project list/graph/detail summary 不返回 full content。
   - Full content 只由 template editor 与 project agent-context endpoint 返回。
   - Execution events/run logs/export 默认只记录 hash/path/source，不记录 full content。

### 测试

- Pydantic model validation tests。
- Hash helper unit tests。
- Contract tests for create/update payload shape。
- DTO tests：summary payload 不含 `content`；full endpoint 含 `content`。

### 验收

- API 模型能表达 template、snapshot、创建时复制、停用与微调。
- Managed manifest 规则能区分 Cairn-managed stale file 与 unmanaged conflict。
- 未实现业务逻辑前，测试能描述预期失败路径。

### 审查点

- 不把 template id 当成 execution-time source of truth。
- 不把 AGENTS.md 内容塞进 `execution_runs` 核心列。

## Phase 1: Schema 与 Migration

### 目的

为 template 与 project snapshot 建立可迁移、可 fresh schema 创建的数据结构。

### 步骤

1. 修改 `cairn/src/cairn/server/schema.py`，新增：
   - `agent_context_templates`
   - `project_agent_contexts`
2. 新增 migration，例如 `0009_agent_context.py`。
3. 表结构建议：
   - `agent_context_templates(id PRIMARY KEY, name, description, kind, content, content_hash, created_at, updated_at)`
   - `project_agent_contexts(project_id, kind, enabled, source_template_id, source_template_hash, content, content_hash, created_at, updated_at, PRIMARY KEY(project_id, kind))`
4. 对 `kind` 加 CHECK：MVP 仅 `agents_md`。
5. `project_agent_contexts.project_id` 外键级联删除。
6. 删除 template 不级联 project snapshot；`source_template_id` 保留普通文本或 nullable reference with `ON DELETE SET NULL`。建议普通文本，避免删除模板影响 snapshot。
7. 若使用普通文本，另存 `source_template_name` 可提高 UI 可解释性；MVP 可选。

### 测试

- Migration status/migrate tests。
- Fresh DB schema includes new tables。
- Fresh DB 不只检查 migration status，必须实际查询 `agent_context_templates` 与 `project_agent_contexts` 存在；当前 runner 会对空 DB 执行 `SCHEMA` 后 stamp 全部 migrations，漏改 `schema.py` 会造成“已迁移但缺表”。
- Existing DB apply `0009` 后可读写新表。
- Project 删除后 snapshot 级联删除。
- Template 删除后 project snapshot 保留。

### 验收

- `cairn db migrate` 能从旧 DB 升级。
- `cairn db reset --to v3.2` 或 fresh migrate 后包含新表；命令文案是否仍叫 v3.2 可在实现中顺带评估，但不作为 v3.5 必须改名。

### 审查点

- schema.py 与 migration 同步。
- 不增加旧 DB 长期兼容 facade。

## Phase 2: Server Service 与 API

### 目的

提供稳定 API，供 UI 与 dispatcher 读取，不让 dispatcher 直连 DB。

### 步骤

1. 新增 service helpers：
   - `compute_agent_context_hash(content)`
   - `template_to_model(row)`
   - `project_agent_context_to_model(row)`
   - `get_project_agent_context(conn, project_id)`
   - `upsert_project_agent_context(conn, project_id, body)`
2. 新增 router `cairn/src/cairn/server/routers/agent_context.py`：
   - `GET /agent-context/templates`
   - `POST /agent-context/templates`
   - `GET /agent-context/templates/{template_id}`
   - `PATCH /agent-context/templates/{template_id}`
   - `DELETE /agent-context/templates/{template_id}`
3. 在 `cairn/src/cairn/server/app.py` 手动 include 新 router；当前 app 不会自动发现 router。
4. 扩展 projects router：
   - `POST /projects` 接受 `agent_context`。
   - `GET /projects`、`GET /projects/{project_id}` 与 `GET /projects/{project_id}/graph` 的 project meta 只返回 snapshot summary，不含 `content`。
   - `GET /projects/{project_id}/agent-context`
   - `PUT /projects/{project_id}/agent-context`
5. DTO 分层：
   - `AgentContextSummary`：enabled、kind、content_hash、source_template_id、source_template_hash、updated_at，不含 content。
   - `ProjectAgentContext`：full snapshot，含 content，仅用于 dedicated endpoint 与 create/update response。
   - `AgentContextTemplateSummary` 可用于 list；template detail/create/update 可含 content。
6. Project 创建逻辑：
   - 若 body 包含 `template_id`，读取 template。
   - 使用 body.content override 或 template.content 形成 snapshot。
   - 写入 `project_agent_contexts`。
7. Update snapshot：
   - `enabled=false` 可保留 content。
   - `enabled=true` 必须 content 非空。
   - 更新 content 必须重算 hash。
8. Delete template：
   - 删除模板不改 project snapshots。
9. API 错误：
   - unknown template -> 400 on project create，404 on direct template get/update/delete。
   - empty enabled snapshot -> 422 或 400，保持现有 FastAPI 风格。
   - content 超过 128 KiB -> 422 或 400。

### 测试

- Template CRUD API tests。
- Project create with no context。
- Project create from template。
- Project create from template with content override。
- Template update does not mutate existing project snapshot。
- Project snapshot PUT enable/disable/edit tests。
- Graph/project detail includes agent context summary without leaking unrelated fields。
- `/projects` list does not include full prompt content。
- New router is registered and `/agent-context/templates` is reachable in API smoke/OpenAPI。

### 验收

- UI 与 dispatcher 都能通过 HTTP 获取所需信息。
- API 行为可由 server tests 独立验证。

### 审查点

- Project snapshot 是运行真相；template 只是来源记录。
- 删除 template 不破坏旧 project 可复盘性。

## Phase 3: Dispatcher Client 与 Runtime Materializer

### 目的

把 project snapshot 转成 workspace 内 `AGENTS.md`，并把结果传给 driver。

### 步骤

1. 扩展 `cairn/src/cairn/dispatcher/protocol/client.py`：
   - 增加 `get_project_agent_context(project_id)`，或让现有 `get_project` 返回完整 snapshot。
   - 优先独立 endpoint，减少 dispatcher 对 project detail 大 payload 的依赖。
2. 新增 `cairn/src/cairn/dispatcher/runtime/agent_context.py`：
   - `AgentContextMaterialization` dataclass。
   - `materialize_agent_context(environment, handle, context)`。
3. Materializer 规则：
   - missing -> `enabled=False`，不写文件。
   - disabled -> `enabled=False`，按 ownership manifest 清理 Cairn-managed stale file。
   - kind 不支持 -> diagnostic failure。
   - enabled agents_md -> absolute target path `handle.workspace/AGENTS.md`。
   - ownership manifest -> absolute path `handle.workspace/.cairn/agent-context/agents_md.manifest.json`。
   - target 不存在 -> write target + manifest。
   - target hash 等于目标 hash -> ok, update manifest。
   - target hash 不等于目标 hash，但 manifest 证明 target 是上一版 Cairn-managed file -> overwrite target + update manifest。
   - target hash 不等于 manifest `last_materialized_hash`，或无 manifest 且 hash 不同 -> unmanaged conflict，返回 failure。
   - disabled 且 manifest 证明 target 是 Cairn-managed -> remove target + manifest；disabled 但无 ownership proof -> leave untouched。
4. 将 materializer 接入所有会启动 worker 的任务路径：
   - bootstrap
   - reason
   - explore
   - conclude fallback
   - question/fork/resume/fresh_context
5. Materialization 与 execution lifecycle：
   - Materialization 必须发生在 `ExecutionRun` 已创建/leased 且 event sink 可写之后。
   - materialize conflict/fetch/schema failure 时，写入 standard execution event diagnostic，并通过 v3.2 finish contract 以 failed terminal status 收尾。
   - 不允许在没有 execution record 的情况下“预启动失败”并只写本地日志。
   - Dispatcher 读取 agent context 的 HTTP failure/500/schema mismatch 必须 fail closed；不得退化成 missing/disabled 后静默运行。
6. Execution ledger metadata：
   - 在 create execution metadata 中预置或 materialize 后 patch merged metadata。
   - metadata key 建议为 `agent_context` object，包含：
     - `enabled`
     - `kind`
     - `content_hash`
     - `materialized_path`
     - `manifest_path`
     - `source_template_id`
     - `source_template_hash`
     - `status`: `disabled|materialized|conflict|error`
   - 如使用 `patch_execution`，先读现有 metadata 并 merge，或新增 server-side merge helper，避免覆盖其它 metadata。
7. 在 `run_worker_process(extra_metadata=...)` 可补充 run-log metadata：
   - `agent_context_enabled`
   - `agent_context_kind`
   - `agent_context_hash`
   - `agent_context_path`
   - `agent_context_source_template_id`
8. materialize conflict 时：
   - 写入 execution message/status diagnostic。
   - 以 failed terminal status 收尾。
   - 不启动 worker process。

### 测试

- Materializer unit tests using fake WorkEnvironment。
- Docker/SSH path guard tests if existing fake environment supports it。
- Dispatcher task tests：
  - missing context leaves driver disabled。
  - enabled context writes AGENTS.md。
  - existing same content ok。
  - existing unmanaged different content fails before worker start。
  - existing Cairn-managed stale content is overwritten after project snapshot edit。
  - disabled snapshot removes Cairn-managed target and manifest。
  - disabled snapshot does not delete unmanaged target。
- Metadata tests for execution ledger and run log separately。
- HTTP fetch failure/schema mismatch fail closed tests。

### 验收

- 任一 execution phase 启动前都能得到一致的 AGENTS.md 处理。
- 失败路径不产生半启动 worker。
- 所有 materialization failure 都有 execution event 与 terminal failed status。

### 审查点

- 不在 driver 内调用 server API。
- 不在 prompt 中复制 AGENTS.md 内容。

## Phase 4: Worker Driver Capability

### 目的

让 Pi 在 project snapshot 启用时读取 context files，在未启用时保持当前隔离。

### 步骤

1. 新增小型 `WorkerRuntimeContext` dataclass，传递 per-execution flags，例如 `agent_context_enabled`、`agent_context_kind`。
2. 扩展 worker driver interface，所有会生成 worker argv 的方法都接收 runtime context：
   - `build_execute(worker, prompt, session, runtime_context=None)`
   - `build_conclude(worker, prompt, session, runtime_context=None)`
   - `build_question(worker, mode=..., prompt=..., source_session=..., runtime_context=None)`
3. Base driver 默认把 runtime context 继续传给 execute/conclude，Pi fork override 也必须显式使用。
4. 修改 PiDriver `_wrap_with_models`：
   - 默认仍包含 `--no-context-files`。
   - 当 `runtime_context.agent_context_enabled=True` 且 kind=`agents_md` 时，不传 `--no-context-files`。
5. Healthcheck 仍保持 `--no-context-files`，避免健康检查受 project context 影响。
6. Codex/ClaudeCode/Mock driver 可忽略该 flag；不得误开其上下文机制。

### 测试

- Pi argv unit tests：
  - disabled -> contains `--no-context-files`。
  - enabled -> does not contain `--no-context-files`。
  - healthcheck -> contains `--no-context-files`。
  - conclude fallback enabled/disabled。
  - question fresh_context enabled/disabled。
  - question resume enabled/disabled。
  - question fork enabled/disabled，覆盖 Pi override。
- Base driver compatibility tests for mock/codex/claudecode if existing tests cover build signatures。

### 验收

- 只有 enabled project execution 改变 Pi context-file behavior。
- 健康检查、未启用 project、非 Pi worker 不变。

### 审查点

- 不顺手打开 `--no-extensions`、`--no-skills`、`--no-prompt-templates`。
- 不用 model_profile/endpoint 决定 AGENTS.md。

## Phase 5: UI

### 目的

让用户在自然 workflow 中管理模板、创建 project 时选择并微调、project 内继续编辑 snapshot。

### 步骤

1. 在现有 single-file UI 中新增 Agent Context 管理区域：
   - template list
   - create/edit/delete
   - content textarea
2. 扩展 project create form：
   - template select
   - load template content into editable textarea
   - enable/disable checkbox
   - 支持不选模板但填写 custom content；若 content 非空，默认 enabled=true。
   - 选择模板时若 textarea 已被用户编辑，必须 confirm 或提供明确 replace 行为，避免静默覆盖未保存编辑。
3. 扩展 project settings：
   - snapshot enabled checkbox
   - content editor
   - source template/hash display
   - save snapshot
4. UI state：
   - `agentContextTemplates`
   - `newProject.agent_context`
   - `projectSettingsForm.agent_context`
5. API integration：
   - initial load fetch templates。
   - project create body includes `agent_context` when enabled or content non-empty。
   - project settings PATCH/PUT snapshot via dedicated endpoint。
6. UX guard：
   - enabled + empty content disables save/create。
   - deleting template warns that existing projects keep snapshots.
   - content 超过 128 KiB 时禁用保存并显示简短错误。
   - dirty state 覆盖模板编辑、project create textarea、project settings snapshot。

### 测试

- Server-render static smoke if available。
- Playwright/manual browser smoke:
  - create template
  - create project from template with edit
  - create project with custom-only content
  - edit project snapshot
  - switch template after local edit and verify no silent overwrite
  - disable snapshot and verify settings dirty/save behavior
  - delete template warning states existing projects keep snapshots
  - enabled-empty and over-size validation
  - narrow viewport/mobile overflow check for textareas and controls
  - verify project detail displays source/hash

### 验收

- 用户可完成“选常用模板 -> 微调 -> 创建 project -> 执行使用”的主路径。

### 审查点

- UI 不暗示 template update 会更新 project snapshot。
- 文案短，不把产品说明写成教程。

6. 创建 template，内容加入可观测指令，例如要求报告中出现固定短语。
7. 创建 project，选择模板并微调。

12. 停用 project snapshot 后再次执行，验证 managed `AGENTS.md` 被清理。

   - fork 与 branch continue 使用 branch-local session，不污染 main history。
   - 小 `limit` cursor 分页仍能读到 final assistant 与 terminal status。
   - DB raw payload bytes 同时满足绝对预算与相对缩减。
   - run log/artifact 文件存在且 hash/size 与 execution API raw ref 一致。
16. 用浏览器或 API 完整走创建模板、创建 project、执行、查看 Output/Conversation、编辑/停用 snapshot 的闭环。
17. 测试完毕后关闭测试用 server、dispatcher、浏览器自动化进程等所有监听服务。

已采纳的关键发现：

- `run_worker_process(extra_metadata=...)` 只进 run log，不等于 `execution_runs.metadata_json`；计划已改为显式写入/merge execution ledger metadata。
- “存在且 hash 不同即 conflict”会误伤 Cairn 自己上次 materialize 的旧 `AGENTS.md`；计划已新增 sidecar ownership manifest 与 disabled cleanup。
- Pi context flag 不能只覆盖 `build_execute`，还必须覆盖 `build_conclude` 与 `build_question`，尤其 Pi fork override；计划已改为 `WorkerRuntimeContext` 贯穿三类 argv 构造。
- ProjectMeta 若含 full content 会污染 `/projects` summary；计划已新增 summary/full DTO 分层。
- Materialization failure 必须在已有 execution record 下通过 finish contract 失败收尾；计划已补 fail-closed 与 diagnostic 要求。
- UI/E2E smoke 需覆盖 `cairn/tests/e2e_test.md` 完整流程、长流式输出、unsaved edit、template switch、custom-only、delete warning、enabled-empty、over-size 与 responsive overflow；计划已补。
- Fresh schema 测试必须实际查新表，不能只看 migration stamped 状态；计划已补。

未采纳或降级：

- 未将 template 删除改为强引用保护。理由：snapshot 是执行真相，删除模板不应破坏旧 project；source missing 可由 UI summary 表达。

## 风险与开放问题

- Driver interface 改动可能牵动多个 worker adapter；应优先用小型 runtime context 对象保持兼容。
- Single-file UI 已较大，新增模板管理会增加熵；若 v3.3 前端重构未先完成，UI 改动要克制。
- Workspace `AGENTS.md` conflict 策略偏保守，可能阻塞用户已有 workspace；MVP 用 diagnostic 换确定性。
- `cairn db reset --to v3.2` 命令名与 v3.5 schema 演进可能语义变旧；实现时可决定是否顺带重命名 target，但不应扩大范围。
- 删除 template 后 source display 可能缺模板名；可通过 snapshot 保存 `source_template_name` 缓解。
- Prompt content 可能含敏感操作指令甚至 secret；MVP 通过 endpoint 分层、大小限制、默认不写入 execution events/run logs/export 降低扩散面，但不能替代用户侧 secret hygiene。
- E2E 依赖本机中转、pentestVM 与 Pi CLI；若外部测试环境不可用，应停止并报告，不能把未验证流程写成已通过。
