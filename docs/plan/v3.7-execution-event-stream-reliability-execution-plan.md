# v3.7 Execution Event Stream Reliability Execution Plan

依据：2026-05-23 线上故障报告（`proj_010_ex091` / `proj_008_ex074` event key conflict、resume/fork 不稳定、Output 实时预览卡顿）
架构依据：`docs/architecture/cairn-architecture-ssot.md`
验收依据：`cairn/tests/e2e_test.md`
日期：2026-05-26
状态：已审查计划草案

## 0. 目标边界

目标是彻底修复 fork/resume 稳定性、ExecutionEvent 写入可靠性、Output 实时可见性与可观测性。核心判断：当前故障不是单个 `batch_size` 参数问题，而是 `ExecutionRun` 原子边界、`event_key` 幂等键来源、EventSink 生命周期、dispatcher/server lease 协议、UI 实时状态几个层面混在一起。

必须达成：

- 每一次 worker process 或 branch/follow-up turn 都对应唯一 `ExecutionRun`，不得复用已写事件或已 terminal 的 execution id 重新开始输出。
- `event_key` 只用于稳定幂等键；不得依赖可丢失的内存游标作为跨生命周期事实。
- `ExecutionRun` 的 single-writer 不能只靠 `leased_by`；dispatcher append/finish/patch 必须携带持久化的 `sink_token` 或等价 generation，用于拒绝同 dispatcher 的第二个 stale sink。
- EventSink 的 live flush、projector close、raw summary close、terminal finish 必须是不同语义，重复调用不得生成新事实。
- 409 event-key conflict 必须 fail-fast 并带诊断，不能继续把失败批次滚到 251+ 触发 422。
- Output UI 必须能在长任务中持续看到 running/status、stream preview、last event age、错误诊断；不能长时间空白让用户误判卡死。
- 日志必须足以定位：哪个 execution、sink token、batch、event key、queue depth、server canonical hash diff、branch/session action、run log ref。

非目标：

- 不恢复 `/questions`、`/runs/*/transcript`、`run_provenance` 等旧路径。
- 不把完整 raw stdout/stderr 写入 DB；完整 raw 仍属于 run log/artifact。
- 不为旧 DB 中已经重复的 raw metric 自动做破坏性 migration；可提供显式 maintenance/diagnostic 查询。
- 不新增 `finishing` DB status；若 UI 需要展示 finishing，应从 EventSink/metadata/last event 派生。

## 1. Proposed Architecture Delta

当前 SSOT 已要求 `ExecutionRun` 是运行层原子、`ExecutionEvent` 是 Output/Conversation 主数据源、terminal status 走 finish barrier、event_key 是 immutable idempotency key。本计划不改变这些原则，但需要把隐含约束明确成实现契约：

- `ExecutionRun` single writer：一个 execution 在 `leased/running` 期间只能由一个 dispatcher-owned run sink 写入。`leased_by` 表示 dispatcher owner，`sink_token`/`sink_generation` 表示该次 process/sink writer；append、finish、dispatcher patch 都必须校验 owner + sink token。terminal 后只允许同 key 同 canonical event 的 idempotent replay，不允许追加新事件。
- `EventSink` state machine：`open -> running -> finishing -> terminal/failed`；`flush_live()` 不关闭 projector/raw summary，`finish()` 才生成 final projector events、raw storage metric、terminal status，并通过 finish contract 一次性提交最后批次。
- `event_key` source contract：语义事件优先使用 upstream stable id（session id、toolCallId、message/turn identity）；raw preview 使用 `execution_id + stream + chunk ordinal`，该 ordinal 只在 single-writer execution 内有效。若事件无法提供稳定幂等键，应让服务端 append 普通事件，不伪造跨重启幂等性。
- `server append guard`：dispatcher append/finish/patch 需要检查 execution 状态、owner 与 sink token；terminal 后 reject 新事件，允许同 key 同 canonical replay；409 只返回短错误，server 日志只输出 hash/shape diff，不输出 raw payload preview。
- `server-internal event channel`：branch initial user event、manual conclude terminal event 等 server 内部写入，不走 dispatcher append 权限模型；它们必须使用受控 internal helper，保持 event_key 幂等和整批原子性。
- `branch turn contract`：每次 branch message 创建新的 pending question execution，并原子写入初始 user event；dispatcher 只能 claim pending execution；fork/resume 多轮在同一 branch 下追加 executions，不复用 source execution。

SSOT 生命周期：本计划确认后，Implementation Phase 0 应在 `docs/architecture/cairn-architecture-ssot.md` 的 Pending Architecture Deltas 增加 v3.7 标记。实现与验收完成后，将上述 delta 合并到 SSOT 主体第 3/4/5/7 节并移除 Pending 标记。

### 步骤

  - `proj_010_ex091`：finish 阶段重复 raw-storage metric / repeated 409。

## Phase 1: Server Lease / Append / Finish Contract

### 目的

由 server 持久层强制 execution single-writer 和 terminal barrier，不能只靠 dispatcher 自律。

### 步骤

- 增加持久 single-writer token：
  - schema/model/API 为 dispatcher-owned execution 增加 `sink_token` 或等价 `lease_token`/`sink_generation`。
  - `lease_execution()` 生成并返回 token；dispatcher EventSink 初始化必须持有 token。
  - append、finish、dispatcher patch 必须携带 token；`leased_by` 相同但 token 不同也必须拒绝。
- 在 dispatcher `append_execution_events()` 增加状态、owner、sink guard：
  - 允许 `leased/running` 且 `leased_by == dispatcher_id` 且 `sink_token` 匹配写事件。
  - pending execution 的 dispatcher append 返回 409，且不消耗 seq/project_seq。
  - terminal 后只允许整批 keyed events 全部已存在且 canonical 一致；否则整批 409。
- 新增 server-internal append helper：
  - branch message 创建 pending question execution 时，用 internal helper 原子写入 user event。
  - manual conclude 用 internal terminal barrier 写 terminal status event + terminal patch。
  - internal helper 不绕过 event_key canonical/idempotency，不允许部分写入。
- `finish_execution()` 保持 final events + patch 原子屏障，并定义 duplicate finish canonical：
  - terminal event 必须同 key 同 canonical event；unkeyed terminal replay 409。
  - patch status/returncode/error/session 字段必须与当前 terminal row 等价；unset 与 null 的等价关系要测试固定。
  - metadata 只允许幂等子集/同值 merge，不允许改变既有值。
- `lease_execution()` 确认 pending execution claim 与 intent execution create+lease 不会复用旧 execution id。
- branch message 创建的 question execution 只停留在 pending；dispatcher 通过 claim endpoint 取走，不走旧 heartbeat/claim 混合路径。
- 增加 server-side conflict diagnostic：
  - 日志输出 `request_id/path/execution_id/status/leased_by/request_dispatcher/sink_token_hash/event_key/existing_event_id/existing_type/new_type/existing_ts/new_ts/existing_payload_hash/new_payload_hash/payload_size_bytes/changed_top_level_keys`。
  - server 没有 dispatcher secrets 上下文，禁止输出 raw payload preview；response 保持短错误。
- 增加 route/validation 层 422 诊断：
  - `events max_length=250` 在 Pydantic validation 发生，必须在 router/middleware 层记录 `path/execution_id/request_event_count/limit/content_length/request_id`。
  - 不把 251 个 event input 回显进日志或 UI。
- 对 dispatcher patch 增加 owner/sink guard：
  - heartbeat、running patch、failed patch、session metadata patch 都必须校验 owner + sink token。
  - manual conclude/request-conclude 使用 internal service helper，不走公开 dispatcher patch 权限模型。

### 测试

- API 测试覆盖 append owner/status/sink guard、terminal replay、新事件拒绝、mid-batch rollback、duplicate finish。
- API 测试覆盖 pending dispatcher append 409，但 branch initial user event 仍通过 internal helper 可见。
- session lock 测试覆盖 resume lock 在 terminal finish/failed/expiry 后释放，failed/cancelled available session 仍可作为 source。

### 验收

- 不可能在 terminal execution 上追加新 Output。
- 不可能由第二个 dispatcher 或同 dispatcher stale sink 对同一个 running execution 写事件。
- 409 日志可用 hash/shape 直接定位 canonical diff，不再只看到 `Event key conflict`，且不泄漏 raw payload。

### 审查点

- manual conclude terminalization 必须仍先写 terminal status event 再 terminal patch，不能破坏 v3.6 路径。
- branch message 初始 user event 不能被 dispatcher append guard 误杀。

## Phase 2: EventSink 状态机与确定性 Key

### 目的

重写 EventSink 生命周期，使 live preview 快、finish barrier 稳、失败可诊断。

### 步骤

- 将 `ExecutionEventSink.close()` 拆成明确方法：
  - `flush_live()`：只发送当前 queued events，按 `MAX_APPEND_EVENTS <= 250` 切片。
  - `flush_projector_partial()`：仅在 projector 支持 partial drain 时使用；默认不 close projector。
  - `finish(terminal_status, patch_fields)`：关闭 projector、生成 raw summary、追加 terminal status、走 finish API。
  - `abort_with_diagnostic(error_code, detail)`：用于 409/422/queue overflow 等协议失败。
- raw preview key 改为 `execution_id:raw:<stream>:<chunk_ordinal>`；raw storage metric 改为每 stream 最多一个 final key：`execution_id:raw-storage:<stream>:final`。
- semantic projector key 使用 upstream stable identity：
  - session：`execution_id:session:<session_id>`
  - tool：`execution_id:tool:<toolCallId>:<phase>`
  - assistant message：`execution_id:message:<turn/message/content identity>:<phase>`
  - status：`execution_id:status:<running|succeeded|failed|cancelled|diagnostic-code>`
- 409 fail-fast：
  - 清空/隔离当前失败队列，停止继续 live append。
  - 通过 finish barrier 或 fallback patch 将 execution 标记 failed，`error_code=event_key_conflict`。
  - 写 run log diagnostic，指向原始 raw stream。
- 422 too_long：
  - 通过 batch slicing 防止正常路径出现。
  - 若 server 仍返回 422，作为 protocol bug fail-fast，不重试膨胀队列。
- 对 live preview 设置 bounded latency：
  - running status 立即 patch + append。
  - stdout/stderr preview 至少每 1 秒或每 N chunks flush。
  - queue 超限时降级为 diagnostic + raw ref，不无限缓存。
- EventSink 初始化即生成并记录 `sink_token/sink_id`：
  - run log `run_started` metadata 写入 `execution_id/sink_id/sink_token_hash`。
  - 每个 append/finish log 带 `run_log_id/run_log_path/sink_id/batch_id`。
  - fatal diagnostic 同步写 run log 结构化记录。
- 失败分类使用明确 `failure_kind`：
  - `append_conflict`, `append_http_timeout`, `append_http_error`, `validation_too_long`, `queue_overflow`, `process_timeout`, `heartbeat_cancelled`, `finish_barrier_failed`, `fallback_patch_failed`。
  - 不再用 `append_timeout` 覆盖所有非 2xx。

### 测试

- dispatcher unit 覆盖：
  - live flush 不 close projector。
  - repeated `finish()` idempotent，不重复 raw metric。
  - batch slicing 永不超过 250。
  - 409/422 fail-fast 且不会继续滚雪球。
  - queue overflow 只产生一次 bounded diagnostic，记录 high-water/drop 统计。
  - terminal status 与 final assistant message 同批或有序提交，terminal 不抢跑。

### 验收

- 长输出每 1-2 秒可见新 preview 或状态更新时间。
- 任何单批 append events 数量 `<= 250`。
- 出现 409 后日志只有一次主诊断，不再每秒刷几十条 append_timeout。
- 每类失败都能从日志跳到 `execution_id -> sink_id -> batch_id/event_key -> run_log_ref`。

### 审查点

- 不把 raw stream 完整写回 DB；bounded preview/ref/metric 边界保持。

## Phase 3: Branch / Resume / Fork 稳定性

### 目的

确保 fork/resume 的 session lineage 与 execution lifecycle 正确，解决“旧对话 resume 失败”和“新出的都无法 claim”。

### 步骤

- 梳理 `branches.py`：
  - 清理 `_source_value()` 后不可达重复代码。
  - `branch_continue` 必须使用 branch-local latest successful available session。
  - resume/follow-up 必须锁本轮 `remote_session_in`，第二轮 resume 应锁 branch-local latest session，不误锁旧 source session。
  - `fork_initial` 不锁 source session，后续 `branch_continue` 使用 branch-local session。
- dispatcher question claim：
  - pending question execution claim 成功后才启动 worker process。
  - worker process 失败、event sink 失败、健康检查失败都必须 terminalize execution。
  - failed/cancelled 但 session available 的 execution 可作为 source，UI 只展示 warning，不阻断创建。
- 检查 claim guard：
  - open intent active state 只来自 active execution projection，不再读 `Intent.worker`。
  - stale leased/running execution 过期后必须变为 terminal diagnostic 或可重新调度的新 execution，不能卡住 intent。
  - branch/question execution 没有 `intent_id`，必须纳入 stale execution expiry；过期时释放 `execution_session_locks`。

### 测试

- server/API：
  - resume source lock 冲突、finish release、failed source available 仍可 resume。
  - fork first turn -> branch_continue 多轮 session lineage。
  - resume 多轮不复用 source execution id，第二轮锁实际 branch-local input session。
  - stale branch question execution expiry 后释放 session lock。
- dispatcher:
  - question task 每条 branch message 新 execution。
  - dispatcher restart 后不会对旧 execution 重建 sink 从 `status:1` 写入。

### 验收

- 连续执行：source -> fork turn1 -> fork turn2 -> resume turn1 -> resume turn2；每一轮都是新 execution，branch timeline 完整。
- source execution 事件不会被 fork/resume 新 turn 污染。

### 审查点

- 不将 fork 临时输出混入 source Output；resume 结果进入主 Output history。

## Phase 4: Output UI 实时预览与状态

### 目的

让用户能判断 worker 是运行、卡住、输出中断、等待 finish，还是失败。

### 步骤

- Output/Conversation 轮询策略：
  - active execution 使用短间隔轮询或已有机制的低延迟刷新。
  - 使用 endpoint-scoped cursor，cursor invalid 时重置并显示诊断，不静默跳读。
  - 对长输出 append 增量渲染，避免每次全量重算导致 UI 卡顿。
- 状态展示：
  - DB execution status 仍为 pending/leased/running/succeeded/failed/cancelled；`finishing` 只能作为 UI derived state，不新增 DB status。
  - `last_event_age = now - max(event.ts)`；`last_heartbeat_age = now - execution.last_heartbeat_at`；run log ref 来自 execution metadata。
  - EventSink diagnostic 使用独立 `diagnostic` event type，或 `payload.diagnostic=true, visibility=debug, failure_kind=...`；Conversation 主流不得把它当普通 assistant/system message。
  - diagnostic 默认折叠，摘要 <= 2KB，可展开查看 bounded detail；不把 422 大 payload 整段铺出来。
- Conversation compaction：
  - partial assistant 按 stable stream/message key 压缩。
  - terminal assistant message 覆盖 running partial。
  - tool running/result 生命周期不被误合并。
- Raw/Debug：
  - DB raw preview 只显示 bounded preview。
  - 完整 raw 指向 run log/artifact ref。

### 测试

- 前端静态 guard 测试覆盖：
  - 不调用旧 `/questions` 或 `/runs/*/transcript`。
  - endpoint-scoped cursor 使用。
  - diagnostic truncation。
- Browser smoke：
  - fake/测试 worker 每 1 秒输出唯一 marker；DOM 在 2 秒内显示 running，5 秒内看到至少 3 个递增 marker，运行中 `last_event_age < 3s`。
  - 409/failed diagnostic 显示简短，不爆屏。
  - 1000+ stdout/diagnostic events 下 UI 可交互，DOM 卡片数量有上限或经过压缩，浏览器 console 无 error，轮询/刷新不乱跳滚动。
  - seeded fixture：assistant partial A + delta B + final AB + status succeeded 只显示最终 AB 一次；两个不同 assistant 回合不得合并。
  - foreign cursor 触发 400 后，UI 清空对应 cursor、短诊断、全量重拉，不丢 terminal/final message。

### 验收

- 用户无需看后台日志即可判断当前状态。
- 长任务不出现“UI 空白十几秒但后台其实在跑”的体验；Playwright 以 1s marker 验证。
- fork turn 关闭与刷新后不混入 source；resume turn 刷新后进入 source history。

### 审查点

- UI 不解析 backend-specific stdout JSONL 来生成主 Conversation；语义事件仍由 dispatcher projector 写入。

## Phase 5: 可观测性与运维诊断

### 目的

让下一次问题能靠日志和 DB 快速定位，不再靠人工猜链路。

### 步骤

- dispatcher structured logs 增加字段：
  - `execution_id`, `project_id`, `intent_id`, `branch_id`, `session_action`
  - `request_id`, `dispatcher_id`, `leased_by`, `sink_id`, `sink_token_hash`
  - `run_log_id`, `run_log_path`, `batch_id`, `batch_event_count`, `queue_depth`, `queue_high_water`
  - `first_event_key`, `last_event_key`, `failure_kind`, `operation`, `attempt`, `server_status`, `elapsed_ms`
- server append/finish logs：
  - conflict diff 使用 hash/shape，不输出 raw payload preview。
  - terminal replay、new terminal append rejected、owner mismatch 分开打点。
  - route validation 422 在 router/middleware 层记录 event count 和 request shape。
- diagnostic events：
  - event sink failure 生成 `diagnostic` event 或 debug-visible diagnostic payload，必须 bounded、deduped，不进入普通 Conversation/fact content。
  - execution metadata 写入 `event_sink_summary`：flush_count、failed_flushes、queue_high_water、dropped_total、dropped_by_type、first/last_dropped_event_key、last_successful_flush_at、terminal_barrier_failures、fallback_patch_failures。
- 提供只读诊断命令或文档 SQL：
  - 查重复 raw metric。
  - 查 terminal 后追加事件。
  - 查同 intent active executions。
  - 查 stale locks。

### 测试

- 单元测试检查日志字段或 diagnostic payload shape，捕获日志并断言字段齐全。
- API 测试检查 409 response 不泄漏大 payload。
- 注入假 secret/API key/raw payload，断言 server/dispatcher 日志和 UI diagnostic 不泄漏。
- 五类失败 409/422/HTTP timeout/queue overflow/terminal barrier failure 均有日志捕获测试，且无重复刷屏。

### 验收

- 从一条 409 日志能定位 existing/new event 差异和 run log。
- 后台日志不会出现连续刷屏同一 batch 的噪音。
- 从 UI diagnostic 或一条主日志能跳转到 `execution_id -> sink_id -> batch_id/event_key -> run_log_ref -> server conflict hash`。

### 审查点

- 不把 secret/API key/raw 大 payload 打进日志；遵守现有 redaction。

## Phase 7: 端到端验收

### 目的

按用户验收要求走真实流程，而不是只靠 unit/API 测试。

### 环境

- 使用 `cairn/tests/e2e/cairn.e2e.db`。
- 使用 `dispatch.dev.yaml` 或测试专用配置。
- 端口使用临时高端口，避免占用用户常用服务。
- 可用 `cairn/tests/e2e_test.md` 中 pentestVM SSH 凭据准备远程 worker。
- 测试结束关闭 server/dispatcher/browser 等监听服务。

### 必跑流程

1. 启动 server + dispatcher。
2. 创建测试 project，跑一个能产生长 stdout/tool stream 的 worker execution。
3. 验证 Output UI：
   - 2 秒内显示 running。
   - worker 每 1 秒输出唯一 marker，5 秒内至少看到 3 个递增 marker。
   - 长输出期间 `last_event_age < 3s` 或 preview 持续更新。
   - terminal 后最终 assistant/status 不丢。
4. 对 successful execution 创建 fork：
   - fork turn1 有独立 branch execution。
   - fork turn2 使用 branch-local session。
   - fork 输出不污染 source Output。
   - 关闭 fork thread 并刷新页面后，source Output 仍不含 fork marker。
5. 对 source 或 failed-but-session-available execution 创建 resume：
   - resume turn1/turn2 都是新 execution。
   - 本轮 input session lock 生效，finish/failed/expiry 后释放。
   - resume 结果进入主 Output history，刷新后仍可见。
6. 人工注入或模拟 event append 409/422/queue overflow/finish barrier failure：
   - UI 显示简短 diagnostic。
   - dispatcher 不继续刷屏，不出现 251 too_long。
   - 日志可关联 run log，且无 secret/raw payload 泄漏。
7. 浏览器刷新页面：
   - branch/source timeline 不丢事件。
   - active/terminal 状态稳定，不抖动、不回到 claimable 假状态。
8. foreign cursor 注入：
   - API 返回 400。
   - UI 显示短诊断后重拉，不静默跳读，不丢 final message。

## 独立审查摘要

复杂度分级：`architecture-or-runtime`，高风险，要求 4+ fresh-context reviewers。

- Reviewer D（UI/UX 与 E2E 验收）：已完成。接受其意见：把实时预览验收从口号改为 Playwright 硬指标（2s running、5s 三个 1s marker、last_event_age < 3s）；补 fork/resume 刷新隔离、1000+ event 不爆屏、foreign cursor 恢复、final assistant fixture。

重要 rejected/保留项：

- 暂不把 SSE/WebSocket 纳入本轮必做。理由：当前故障根因在 execution/event contract 与 sink 生命周期；先用 bounded polling + last_event_age 达成验收，若 Playwright 仍不能稳定满足实时性，再升级 transport。
- 暂不自动清理历史 DB 重复 raw metric。理由：这属于历史数据维护，不影响新 contract 验收；计划只要求提供诊断 SQL/maintenance 入口。

## 风险与开放问题

- schema 需要增加 `sink_token` 或等价 `lease_token/sink_generation`，否则同 dispatcher stale sink 无法被 server 区分；实现时需迁移 fresh schema 与当前支持升级路径。
- 是否引入 SSE/WebSocket：当前计划优先优化 polling 和 bounded latency；若 UI 仍达不到 1-2 秒可见，再评估 SSE。
- 历史 DB 重复 metric 如何处理：默认不自动迁移；可提供诊断 SQL 或 maintenance command。
- 远程 worker 实际输出格式可能变化：projector key 必须容忍缺失 upstream id，缺失时保守使用 append-only event 或 diagnostic。
