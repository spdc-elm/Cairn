# V3.6 Manual Intent Conclude Execution Plan

依据：2026-05-23 用户需求：“active intent 在 API/worker 卡住时允许人工 conclude；界面给 resume conclude prompt；粘贴 JSON 解析写回；stale worker 显示不能误导；failed worker 的工作仍可继续 conversation/fork/resume。”
E2E 依据：`cairn/tests/e2e_test.md`
架构依据：`docs/architecture/cairn-architecture-ssot.md`
日期：2026-05-23
状态：待执行计划，已吸收独立 subagent review

## 0. 目标边界

### 0.1 用户验收标准

本轮实现必须同时满足下列条件：

- active intent 即使 dispatcher/API/worker 卡住，用户也能手动发起 conclude。
- conclude 界面必须提供一段可复制的 prompt，用于对原 worker session 做外部 resume，让 AI 停止探索、产出报告、返回 JSON。
- 用户粘贴 JSON 后，Cairn 能解析并写入 primary result fact，intent 进入 concluded。
- intent 显示绑定 worker 但 worker 实际已死时，UI 不得继续把它当 active worker；`Request Conclude` 不应再出现 “no active worker/no active execution” 这种前后端语义不一致。
- worker execution 已 failed/cancelled，但只要有 available remote session，Conversation 必须仍能继续，且 fork/resume 能用；否则失败 worker 的已完成工作会白费。
- 实现与验证过程中不得停止或重启正在运行的 server / dispatcher 进程。

### 0.2 当前事实

已读当前代码与 SSOT 后的事实：

- `Intent` 不应承载 live worker lease；active/running 是 `execution_runs.status in ('pending','leased','running')` 的派生状态。
- `GET /projects/{project_id}/graph` 已投影 `active_execution_id`、`latest_execution_id`、`runtime_status`、`worker_name`。
- `intent_to_model()` 目前会用 latest execution 回填 `Intent.worker`。因此 terminal failed/cancelled execution 也可能让 UI 看到 `intent.worker`。
- Web UI 目前用 `selectedIntentRecord().worker` 决定是否显示 `Request Conclude`。
- `POST /projects/{project_id}/intents/{intent_id}/request-conclude` 只接受 active execution；没有 active execution 时返回 409。
- `POST /projects/{project_id}/intents/{intent_id}/conclude` 会调用 `get_claimable_open_intent_or_404()`，active worker 与提交 worker 不同则 409；这正好挡住“人工接管 active intent”的场景。
- `POST /dispatcher/executions/{execution_id}/conclusion-report` 已能把某个 intent execution 的 conclusion report 写成 primary fact，并建立 execution evidence link，但它是 dispatcher 语义 API，不适合直接暴露给 Web UI 做人工导入。
- Branch 创建本身只要求 source execution 有 `remote_session_out_status='available'`，不要求 source execution succeeded；但当前 `_check_branch_availability()` 还会用 `_source_identity_unhealthy()` 拒绝 unhealthy source identity。该 health guard 与用户验收“只要 session available，failed worker 的工作仍可 fork/resume”冲突，本轮必须改成 warning/diagnostic，而不是 branch creation blocker。

### 0.3 核心判断

本轮不是增强 dispatcher 的自动 conclude。用户的问题来自自动链路失效后的人工救援：

```text
stuck/failed active execution
  -> user copies manual conclude prompt
  -> user resumes original remote session outside Cairn automatic dispatcher path
  -> model returns accepted JSON
  -> user pastes JSON into Cairn
  -> server validates JSON and atomically claims intent conclusion
  -> server writes primary fact + EvidenceLink provenance
  -> active execution, if still active, is terminal-marked through a manual terminal barrier
```

因此实现应新增一条 user-facing manual import path，而不是让 Web UI 调 dispatcher-only API，也不是把 `Intent.worker` 重新定义为 live lease。

Health policy 必须明确：user-initiated fork/resume 的准入条件是 source execution 有 available remote session 且 worker capability 支持该 mode。`worker_runtime_health=unhealthy` 只能作为 UI/API warning，不得阻止 branch creation；实际 follow-up execution 若仍无法运行，由 dispatcher healthcheck/finish 记录失败。

### 0.4 SSOT 生命周期

本计划触及核心 API、Intent/Execution 边界、Conversation/fork/resume 行为，实施完成后需要检查并更新 SSOT。

预计 SSOT 更新点：

- 第 3 节运行层主链路：补充 manual conclude import 是 `ExecutionRun -> Fact projection` 的人工投影路径；它仍不让 `Intent` 承载 live runtime。
- 第 4 节 Conversation 与 Session：明确 failed/cancelled execution 只要有 available remote session，仍可作为 fork/resume source。
- 第 7 节 UI 投影规则：UI active state 必须来自 execution projection，不得用 `Intent.worker` 判断 running。

计划阶段不修改 SSOT 主体。实现阶段若代码落地，最后必须同步 SSOT 主体；不需要 Pending Delta，因本改动是对现有边界的澄清与补全，不是替换主架构。

### 0.5 非目标

- 不恢复 `/questions`、`/runs/*/transcript`、`run_provenance`。
- 不让 server 解析 backend-specific raw stdout 作为 Conversation 主路径。
- 不让 dispatcher 自动重试或重启卡住 worker。
- 不承诺自动杀远端进程；manual conclude 成功后只做 DB terminal 标记。
- 不引入新核心概念如 `Claim`、`ManualRun`。
- 不做 React/Vite 前端重构。

## Phase 0: Contract First 与 RED 基线

### 目的

先把用户验收标准转成失败测试，避免实现时只修按钮不修语义。

### 步骤

1. 新增 `test_v36_manual_intent_conclude_api.py`。
2. 新增 manual prompt API 的 RED：
   - active execution 时返回 prompt、source execution id、session 信息、expected JSON shape。
   - latest failed execution 且有 available remote session 时也返回 prompt。
   - open intent 无任何 execution 时仍可返回 prompt，但标记 `source_session_available=false`。
3. 新增 manual import API 的 RED：
   - active execution 被其他 worker claim 时，人工导入仍能 conclude intent。
   - 粘贴 wrapped JSON：`{"accepted": true, "data": {"title": "...", "description": "..."}}` 成功写入 fact。
   - 粘贴 bare JSON：`{"title": "...", "description": "..."}` 成功写入 fact。
   - `accepted=false`、缺 `description`、空 `description` 返回 400。
   - 已 concluded intent 再导入返回 409。
   - manual conclude 成功后，如果存在 active execution，则该 execution 进入 terminal status，`error_code='manual_concluded'`。
   - source execution provenance 必须校验 same project + same intent；foreign project、wrong intent、missing execution 分别返回明确 404/400。
   - manual fact 必须有 `derived_from` evidence link；若注册 report artifact，则还必须有 `supports` evidence link。
   - 两个并发 manual submit 只能产生一个 primary fact；失败方返回 409。
   - manual conclude 后 dispatcher late `finish(succeeded)` 与 late `conclusion-report` 不得生成第二个 fact，也不得破坏已写 fact。
4. 新增 `test_v36_failed_execution_conversation_availability.py`：
   - failed execution + `remote_session_out_status='available'` 可以 create fork branch。
   - failed execution + `remote_session_out_status='available'` 可以 create resume branch。
   - failed execution + available session + unhealthy runtime health 仍可以 create fork/resume branch，但 response/projection 带 warning。
   - failed execution + no available session 仍返回 `Source execution has no available remote session`。
5. 新增/更新 UI guard：
   - `Request Conclude` 按钮不再由 `intent.worker` 单独控制。
   - `Manual Conclude` 对 open intent 可见。
   - failed/latest worker 显示为 terminal history，不触发 active worker action。

## Phase 1: Server Manual Conclude API

### 目的

提供清晰的人工导入边界：server 负责生成 prompt、解析 JSON、写 fact、标记 stale active execution；dispatcher 不参与。

### 步骤

1. 在 `models.py` 增加请求/响应模型：
   - `ManualConcludePromptResponse`
   - `ManualConcludeRequest`
   - `ManualConcludeParsedPayload`
2. 在 `routers/intents.py` 增加：
   - `GET /projects/{project_id}/intents/{intent_id}/manual-conclude-prompt`
   - `POST /projects/{project_id}/intents/{intent_id}/manual-conclude`
3. prompt 生成规则：
   - 读取当前 graph export，内联或摘要化放入 prompt；优先复用 `explore_conclude.md` 的规则文本。
   - 明确这是人工 conclude phase：停止探索，不等待命令，不继续解决 goal。
   - 如果 latest/active execution 有 `remote_session_out_status='available'`，提示用户对该 remote session 做 resume。
   - 如果 execution metadata 有 `report_path`，要求写报告到该路径；否则要求在 JSON description 中只写短事实，并在 UI 里提示“无 report path 可自动关联”。
   - 输出格式只允许 raw JSON object。
4. JSON 解析规则：
   - 抽出 shared parser，例如 `cairn.shared.conclusion_payloads.parse_manual_conclusion_payload()`。
   - parser 内部可复用现有 `extract_json_object()` / explore payload validation 逻辑，但模块归属必须是 shared，不是 dispatcher。
   - accepted false 在 manual import 中视为不可 conclude，返回 400；用户可取消，不写 rejected fact。
5. 写入规则：
   - 新增 service helper，例如 `submit_manual_intent_conclusion()`。
   - 如果 request 指定 `source_execution_id`，必须校验 execution 存在、属于同 project、属于同 intent；否则拒绝。
   - 校验通过后，fact `produced_by_execution_id` 指向它。
   - 若未指定，优先 active execution，其次 latest execution；都没有则为空。
   - `produced_by_intent_id` 必须写入 intent id。
   - metadata 至少包含：
     - `source: manual_conclude_import`
     - `actor`
     - `source_execution_id`
     - `raw_json`
6. 原子性与 provenance：
   - manual helper 必须在同一 DB transaction 内完成：分配 fact id、条件式 claim intent、插入 fact、插入 evidence links。
   - 条件式 claim 推荐为 `UPDATE intents SET concluded_fact_id=?, concluded_at=? WHERE id=? AND project_id=? AND concluded_fact_id IS NULL`，检查 affected rows；0 rows 则返回 409 并回滚 fact/evidence。
   - 有 `source_execution_id` 时必须创建 `derived_from` evidence link。
   - 如果 UI/API 允许提交 report artifact/path，则 server 必须注册 artifact 并创建 `supports` link；否则 prompt 只能把 report 当外部用户参考，不能暗示已被 Cairn evidence ledger 追踪。
7. active execution 收尾：
   - manual conclude 成功后，查该 intent 所有 active executions。
   - 收尾必须是“等价 terminal barrier”：先 append 一个 status execution event，稳定 `event_key` 如 `{execution_id}:status:manual-concluded`；再把 execution 条件式标为 `cancelled`、`error_code='manual_concluded'`、`error_detail='intent manually concluded by user import'`。
   - 使用 conditional SQL 或 re-read skip：只更新 `status IN ('pending','leased','running')` 的 execution。若 dispatcher 已抢先 finish，不得回滚已写 manual fact。
   - 不发送 kill，不调用 dispatcher，不停止进程。
8. late dispatcher 行为：
   - manual terminalization 后，dispatcher late `finish` 可能收到 409；这是 benign/superseded diagnostic，不得破坏已生成 fact。
   - dispatcher late `conclusion-report` 必须返回 409 “Intent already has a primary result fact”。
   - 如果 late finish 携带 raw/final events，当前计划不保证写入 terminal execution；run log 文件仍由 dispatcher/runtime 保存。实现可后续增加 superseded artifact import，但不作为本轮验收。

### 测试

运行 Phase 0 的 server API 测试，并补一个 transaction 断言：

```bash
PYTHONPATH=cairn/src python -m pytest cairn/tests/server/test_v36_manual_intent_conclude_api.py -q
```

### 验收

- active intent 被其他 worker claim 时，manual import 不被 claim 校验阻塞。
- 成功导入后 intent 有 exactly one primary result fact。
- fact 有正确 `produced_by_intent_id`、`produced_by_execution_id` 与 `derived_from` evidence link。
- active execution 不再让 project summary 显示 working intent。
- 同一 intent 第二次 manual conclude 返回 409。
- 并发 duplicate submit 只能成功一次。
- dispatcher late finish / late conclusion-report 不破坏 manual fact。

### 审查点

- 不要让 manual API 复用 dispatcher router 路径名；这会混淆权限和职责。
- 不要把 manual JSON parsing 放到 Web UI 作为唯一校验；前端只能做预览，server 必须重新校验。
- 不要用裸 `patch_execution(status='cancelled')` 代替 terminal event barrier。

## Phase 2: Stale Worker 与 Intent Runtime Projection 修正

### 目的

修复“intent 显示绑定 worker，但 request conclude 却 no active execution”的语义错位。

### 步骤

1. 保持 `Intent.worker` 向后兼容，但前端不再用它判断 active。
2. 在 graph projection 中明确输出，并优先新增字段：
   - `active_execution_id`
   - `latest_execution_id`
   - `runtime_status`
   - `active_worker_name`
   - `latest_worker_name`
   - `branch_warnings` 或 conversation resolution 中等价的 warning list，用于表达 `worker_environment_unhealthy` 等非阻断状态。
3. 如果不想扩 API 字段，前端至少必须使用现有：
   - active 判断：`Boolean(intent.active_execution_id && ['pending','leased','running'].includes(intent.runtime_status))`
   - latest terminal 判断：`['succeeded','failed','cancelled'].includes(intent.runtime_status)` 且无 `active_execution_id`
4. 更新 UI label：
   - active：`Running` / `Concluding`
   - latest failed：`Failed`
   - latest cancelled：`Cancelled`
   - no execution：`Unclaimed`
5. `Request Conclude` 只对 active execution 显示。
6. `Manual Conclude` 对所有 open intent 显示，active 与 terminal 都可用。
7. 旧 `worker` / `worker_name` 只能作为 display/history 兼容字段；claim、heartbeat、request-conclude、delete/release 等按钮不得依赖它判断 active ownership。

### 测试

```bash
PYTHONPATH=cairn/src python -m pytest \
  cairn/tests/server/test_v36_ui_manual_conclude_guard.py \
  cairn/tests/server/test_v32_graph_projection.py -q
```

### 验收

- failed latest execution 不再让 UI 显示可自动 request conclude。
- active execution 仍可 request conclude。
- manual conclude 永远不会因为 `intent.worker` stale 而消失。
- claim/heartbeat/request-conclude 三类 active-worker action 都只由 active execution projection 控制。

### 审查点

- 如果为了快速修复直接让 `intent_to_model()` 不返回 latest worker，需检查所有旧 UI/测试依赖；更保守路线是前端改判断，API 只补清晰字段。

## Phase 3: Failed Execution Conversation / Fork / Resume 保活

### 目的

确保失败 worker 的已产生 session 不浪费：只要 remote session available，用户仍能继续 conversation，并能 fork/resume。

### 步骤

1. Server branch API：
   - 保持 create branch 只要求 `remote_session_out_status='available'`，不新增 `status='succeeded'` 限制。
   - 为 failed/cancelled source execution 增加明确测试。
2. UI conversation resolution：
   - `canAskSelectedConversation()` 不以 execution succeeded 为前提。
   - availability 判断使用 `remote_session_out_status` 与 worker capability，而不是 terminal status。
   - source execution failed 时，Output 仍显示 terminal failure，但 composer/fork/resume 能基于 available session 开启。
3. Health guard：
   - 当前 `_check_branch_availability()` 会因 `_source_identity_unhealthy()` 禁用 fork/resume。
   - 本轮必须改为：worker runtime health 不阻止 user-initiated branch creation；它只产生 warning，例如 `worker_environment_unhealthy`。
   - branch response 或 conversation resolution 必须让 UI 能拿到该 warning，避免按钮看似可用但提交后才失败。
   - dispatcher claim/run 仍可在后续 execution 中根据实际 healthcheck 失败并记录 Output；这不影响 branch/session lineage 的创建。
4. Session lock：
   - resume branch 仍使用 session lock，避免两个 resume 同时污染同一 remote session。
   - fork branch 不锁 source session。

### 测试

```bash
PYTHONPATH=cairn/src python -m pytest \
  cairn/tests/server/test_v36_failed_execution_conversation_availability.py \
  cairn/tests/server/test_v32_branch_api.py \
  cairn/tests/server/test_v32_execution_session_locks.py -q
```

### 验收

- failed execution + available session 可以 fork。
- failed execution + available session 可以 resume。
- failed execution + available session + unhealthy runtime health 也可以 fork/resume，但 UI 显示 warning。
- failed execution + no session 不可 fork/resume。
- resume 仍进入 main output history；fork 不污染 main output。

### 审查点

- 不要通过放宽所有 branch 校验来解决；source session availability 和 capability 仍必须校验。
- 不允许再把 unhealthy health 当 branch creation blocker；否则直接违背本轮用户验收。

## Phase 4: Web UI Manual Conclude Flow

### 目的

让用户能在一个清晰界面中完成 copy prompt -> external resume -> paste JSON -> conclude。

### 步骤

1. 在 selected intent panel 增加按钮：
   - `Request Conclude`：仅 active execution。
   - `Manual Conclude`：open intent always available。
2. 改造或新增 modal：
   - 第一段：只读 prompt textarea，带 Copy 按钮。
   - 显示 `source_execution_id`、remote session kind/id/status。
   - worker type 已知时，显示 copyable resume target hint 或 command template；未知时明确提示需要用户手动选择原 session。
   - 第二段：JSON paste textarea。
   - 第三段：解析预览 title/description/error。
   - Submit 调 `POST /manual-conclude`。
3. 前端解析只做 UX 预览：
   - 能识别 wrapped/bare JSON。
   - 不能绕过 server 校验。
4. 成功后：
   - 关闭 modal。
   - reload project/graph/conversation。
   - selectedNode 可以跳到新 fact 或清空；优先跳到新 fact 便于确认。
5. failed/latest worker 状态展示：
   - worker field 显示历史 worker 时加 terminal label，避免误读为 active owner。
   - active status 使用 `active_execution_id`。

### 测试


### 验收

- active stuck intent 可打开 Manual Conclude。
- failed latest intent 可打开 Manual Conclude。
- stale worker 不再显示自动 Request Conclude。
- source session 不存在时，UI 不显示“请 resume 某 session”的误导文案，而是提示只能粘贴已有结论 JSON。
- 粘贴 valid JSON 后 UI 刷新出新 fact。
- invalid JSON 提示错误，不写 fact。

### 审查点

- Modal 文案必须短，但 prompt 内容必须完整；不要把规则散落在多个 UI 文案中。
- 不要把 report path 当必填；现实中 failed/stale execution 可能没有可用 report path。

## Phase 5: SSOT 与文档同步

### Manual E2E 主流程

在不停止/重启现有 server/dispatcher 的前提下，必须真实走完下列流程：

1. 启动测试 server：
   - `--db-path cairn/tests/e2e/cairn.e2e.db`
   - 随机或显式高端口
   - `--no-access-log`
2. 启动测试 dispatcher：
   - `--config dispatch.dev.yaml`
   - 指向上一步 server URL
   - worker 使用 `pentestVM` SSH + Pi。
3. 创建新 project，environment 选 `pentestVM`，关闭 auto reason，避免自动任务污染验收。
4. 创建一个用于卡住/失败救援的 intent，并通过 dispatcher 产生至少一个带 `remote_session_out_status='available'` 的 execution。
5. 制造 stale/failed 场景：
   - 可以让后续 execution failed/cancelled，但保留 available session。
   - 如果需要模拟 active stuck execution，只能通过测试 DB/API 标记本轮 execution，不得杀用户进程。
6. 用浏览器自动化打开测试 server UI，选择该 intent：
   - latest failed/stale worker 不显示自动 `Request Conclude`。
   - open intent 始终显示 `Manual Conclude`。
   - worker 历史状态文案不暗示仍有 active worker。
7. 打开 Manual Conclude modal：
   - prompt textarea 可复制。
   - source execution/session 信息显示准确。
   - 没有 available session 时文案不诱导用户 resume 不存在的 session。
8. 在外部 worker session 对原 remote session 做 resume，粘贴 modal prompt，要求模型只返回 JSON。若真实 resume 因模型/中转不可用阻塞，可用同一 source execution 的 session 信息和 prompt 记录为环境阻塞；不能直接改成纯 mock 通过。
9. 把返回 JSON 粘贴回 UI：
   - wrapped JSON 与 bare JSON 至少各测一次，其中一次可走 API，另一次必须走 UI。
   - invalid JSON 或 `accepted=false` 必须提示错误且不写 fact。
10. 提交 valid JSON 后确认：
    - intent 进入 concluded。
    - 新 primary fact 出现在 graph。
    - project working count 下降。
    - fact 有 `produced_by_intent_id`、正确 source `produced_by_execution_id` 与 evidence provenance。
    - 若原 execution 仍 active，它被 terminal-marked 为 manual concluded，且不再驱动 UI active 状态。
11. 对同一 intent 再次提交 manual conclude，确认返回 409 或 UI 等价错误，不生成第二个 primary fact。
12. 模拟 dispatcher late `finish` / `conclusion-report`，确认不会破坏 manual fact，不生成第二 fact。

### Conversation / Fork / Resume E2E

同一轮 E2E 还必须覆盖 failed worker 的 conversation 保活：

1. 选择 failed/cancelled 但 `remote_session_out_status='available'` 的 source execution。
2. 在 UI 创建 fork branch，发送短消息，确认新 execution 使用 source remote session，fork 输出不污染 main output。
3. 在 UI 创建 resume branch，发送短消息，确认结果进入 main output history。
4. 将 worker runtime health 置为 unhealthy 或用测试 fixture 模拟 unhealthy projection，确认 UI/API 只给 warning，不阻止 fork/resume branch creation。
5. 对 no available session 的 execution 尝试 fork/resume，确认仍被拒绝，错误为 `Source execution has no available remote session` 或等价 UI 文案。

### 长流式输出 E2E

按 `e2e_test.md` 的额外要求，本轮最终验收必须覆盖较长流式输出完整同步和正确显示：

1. 在同一测试 project 或独立测试 project 发起 Pi execution，要求输出 320 行，首尾 sentinel 为 `V36-LONG-STREAM-001` 与 `V36-LONG-STREAM-320`。
2. 通过 API 小页分页读取 execution events，确认：
   - 能读到 terminal `status=succeeded`。
   - assistant semantic message 包含首尾 sentinel。
   - 中间行没有明显断裂、重复覆盖或只显示 raw preview。
3. 通过浏览器确认 Output/Conversation 里首尾 sentinel 可见，滚动/刷新后不丢 final assistant message，不因长输出导致窗口抖动、按钮遮挡或输入框错位。
4. 该长流式验证可以复用 v3.4 stream reliability smoke 的 helper，但必须在 v3.6 最终报告中单独列明结果。

## 独立审查摘要

复杂度分类：cross-module-or-protocol。涉及 server API、Execution/Intent projection、UI behavior、Conversation fork/resume policy，但不新增 DB table。

计划要求：至少 3 名 fresh-context reviewer；实际已运行 3 名。

Reviewer 角度：

- Maintainability / architecture boundary：manual conclude 是否破坏 Intent/Execution 边界。
- Operability / failure modes：stuck active execution、duplicate submit、session lock、terminal marking 是否可靠。
- UX / acceptance：按钮状态、prompt、JSON paste、failed worker conversation 是否覆盖用户真实路径。

采纳的 review 修改：

- 明确 manual fact 必须写 `EvidenceLink(derived_from)`；如果注册 report artifact，还要写 `supports` link。
- 明确 manual terminalization 必须包含 terminal status event barrier，不能裸 patch execution。
- 明确 user-initiated fork/resume 不再被 runtime health guard 阻止；unhealthy 只作为 warning。
- 明确 server 不 import dispatcher contracts；结论 JSON parser 抽到 shared。
- 明确新增 `active_worker_name/latest_worker_name`，旧 `worker/worker_name` 只作兼容显示。
- 明确 duplicate/concurrent manual submit 的 conditional barrier 与 race/late finish 测试。
- 明确不停止/重启现有 server/dispatcher 的验证协议。

未采纳项：无。review 中“将验收改窄为 available session 且 health 未禁用”与用户需求冲突，因此选择改变 health guard policy。

## 风险与开放问题

- `Intent.worker` 向后兼容可能继续误导其他代码；本轮先修 UI 判断，后续可考虑 API 模型拆分 `active_worker_name/latest_worker_name`。
- manual prompt 的 report path 不一定可得。实现必须支持无 report path 的情况。
- manual conclude 成功后把 active execution 标 `cancelled` 会与 dispatcher 稍后 finish 竞争。计划把 late finish 409 定义为 benign/superseded，并测试不得破坏 manual fact；后续若需要保留 late final events，可设计 superseded artifact import。
- 用户粘贴错误 JSON 后会产生错误 fact。本轮不新增 undo API；已有 fact edit/update 可修正文案，真正撤销需要后续支持 retraction/reopen 或管理员 DB 备份恢复。
- 前端是单文件 Alpine UI，改动要保持局部，避免顺手做结构重构。
