## 0. 目标边界

### 0.1 核心判断

V3.4 先于 V3.3 执行。V3.3 的 React/TypeScript 前端重构暂缓，不作为本轮依赖。

本轮目标不是重写 UI，也不是把 polling 换成 WebSocket/SSE，而是在现有 v3.2 Execution ledger 上补可靠性边界：

```text
worker stream
  -> dispatcher EventSink
  -> server append events
  -> terminal finish
  -> UI cursor projection
```

计划选择“保守但硬”的路线：

- Server 增加强幂等、cursor scope、`finish_execution` 原子终态。
- Dispatcher 以有界同步可靠写为第一版，不先引入磁盘 spool。
- UI 在现有 `index.html` 上改为完整 cursor 读取与语义事件投影，不等待 V3.3。
- SSH chunk streaming 暂不作为第一关键路径；先加诊断与 E2E，再决定是否升级 reader。

关键约束：

- `finish_execution` 只做通用 ledger 原子写入，不解析、不生成、不补全 worker transcript/final message。
- v3.4 dispatcher 主路径不得再用 `PATCH /dispatcher/executions/{id}` 设置 `succeeded/failed/cancelled`；terminal status 必须经 `finish_execution`。
- 真实 SSH/Pi fork 长回复是 sign-off gate。环境缺失时实现结论为 blocked，不能用 mock E2E 替代用户问题复现。

### 0.2 SSOT 生命周期

当前 SSOT 已新增 Pending Architecture Delta：`v3.4-stream-reliability`，状态 `accepted-for-planning`。

执行期间：

- Phase 0-6：Pending 标记保留，说明 plan 有意偏离 Current SSOT 的 terminal patch/cursor/UI 细节。
- Phase 7：实现、测试、真实 SSH/Pi E2E 通过后，把 delta 合并进 SSOT 主体，更新章节 `3/4/5/7/9`，然后移除 Pending 标记。

### 0.3 非目标

- 不恢复 `/questions`、`/runs/*/transcript`、`run_provenance`。
- 不执行 V3.3 React/Vite 迁移。
- 不把 server 变成 worker transcript parser。
- 不以单纯调大 timeout 作为验收。
- 不承诺旧 DB/API 长期兼容；必要 migration 只服务当前测试与开发 DB。

## Phase 1: Server Event Contract 与 SQLite 写路径

### 目的

让 server 成为可靠事件 ledger：强幂等、cursor scope、短事务、可承受写锁。

### 步骤

1. 在 `db.connect()` 设置 SQLite 写等待：
   - `PRAGMA busy_timeout = 5000` 或等价配置。
   - 保持 WAL 与 foreign keys。
   - `test_v34_sqlite_write_backpressure.py` 必须断言新连接实际带有 busy timeout。

2. 在 `append_execution_events()` 中实现 canonical event 比对：
   - canonical fields：`event_type`、`role`、`payload_json`、`ts`。
   - 同 key 同 canonical event 返回旧 row。
   - 同 key 不同 canonical event 抛 `HTTPException(409, "Event key conflict")`。
   - conflict 不消耗 `seq/project_seq`。

3. 收紧 cursor scope：
   - `list_execution_events()` 的 `after_cursor` 必须属于目标 execution。
   - `get_branch_timeline()` 的 `after_cursor` 必须属于目标 branch。
   - 保留 project-wide cursor 作为内部 ordering，但不允许错用到 endpoint scope。
   - 同 project 但属于其他 execution/branch 的 cursor 必须 400，不得返回空页或跳过早期事件。

4. 增加 append batch 限制：
   - Pydantic model 或 service 层限制单批最多 100 或 250 events。
   - 超限返回 413/422。

5. 保持 transaction 小而短：
   - append 不做额外 projection 或 worker-specific parsing。
   - claim/heartbeat/health update 不在同一请求中读写大 event 集。

- 若 conflict 只打日志仍返回 200，停止。

## Phase 2: Atomic Finish API 与 Terminal Barrier

### 目的

消灭“execution 已 succeeded，但 final events 没落库”的不一致状态。

### 步骤

1. 新增 models：
   - `FinishExecutionRequest`
   - `FinishExecutionResponse`
   - 推荐 shape：`dispatcher_id`、`events: list[ExecutionEventAppend]`、`patch: FinishExecutionPatch`。
   - `FinishExecutionPatch` 是 `PatchExecutionRequest` 的 terminal subset，只允许：`status in succeeded|failed|cancelled`、`returncode`、`error_code`、`error_detail`、`remote_session_out_*`、`metadata`。
   - 不复制完整 patch 能力，不允许 `last_heartbeat_at`、`lease_seconds`、`control_state` 等 non-terminal 字段。

2. 新增 service：
   - `finish_execution(conn, execution_id, body)`
   - 同事务内：
     1. append terminal/final events。
     2. patch execution terminal fields。
     3. release session lock。
   - 任一 event conflict 或 validation error 时整体 rollback。
   - server 只校验通用 event contract、lease ownership、状态迁移与 terminal patch 合法性；不得理解 assistant/session/tool 语义，不得解析 stdout，不得生成 final message。
   - ownership：`dispatcher_id` 必须匹配 `execution_runs.leased_by` 或当前允许的 dispatcher identity；非 owner finish 返回 403/409。
   - 状态迁移：仅 `leased/running` 可 finish 为 terminal；已 terminal execution 不可被新 terminal payload 覆盖。
   - 重复 finish 幂等：同 execution 同 terminal status、同 canonical terminal events、同 patch payload 时返回既有 terminal state；payload 不同返回 409。
   - finish conflict 后必须可重试同一 canonical payload。

3. 新增 router：
   - `POST /dispatcher/executions/{execution_id}/finish`

4. 保留 `PATCH /dispatcher/executions/{id}`：
   - 用于 heartbeat、running、non-terminal patch。
   - v3.4 dispatcher 主路径不得再用 PATCH 设置 `succeeded/failed/cancelled`。
   - 兼容期 terminal PATCH 仅允许旧测试/手工调试，并必须有 guard test 防止 dispatcher production code 调用。
   - Phase 7 合并 SSOT 时写明退场：terminal PATCH 将删除或变成 only-if-no-events debug escape hatch。

5. 终态事件顺序规定：
   - final assistant/session/tool close events。
   - terminal status event。
   - execution terminal status patch。

### 测试

```bash
PYTHONPATH=cairn/src python -m pytest \
  cairn/tests/server/test_v34_execution_finish_api.py \
  cairn/tests/server/test_v32_execution_session_locks.py -q
```

### 验收

- finish 成功后，events 与 execution terminal status 同时可见。
- finish 中 event conflict 时 execution 不 terminal。
- session lock 在 finish terminal 后释放。
- terminal 后 non-terminal patch 被拒绝或不改变 terminal facts。
- duplicate finish 的幂等/冲突语义明确可测。

### 审查点

- 若 dispatcher 仍以 `append final -> patch status` 作为主路径，停止。
- 若 finish API 内部调用旧 `/questions` 或旧 transcript 逻辑，停止。

## Phase 3: Dispatcher EventSink 可靠写与 Question 顺序

### 目的

让 dispatcher 在 server 背压时可控失败或可靠完成，不再静默丢 final。

### 步骤

1. 重构 `ExecutionEventSink`：
   - `batch_size` 恢复为可配置默认值，例如 25。
   - 增加 `max_queue_events`。
   - 增加 `flush_timeout_seconds` / `close_timeout_seconds` 的本地等待预算。
   - 增加 `last_successful_flush_at`、`oldest_queued_at`、`failed_flushes`。
   - `flush()` 返回结构化结果，而不仅是 bool。
   - 不得持有 queue lock 发 HTTP；不得在 diagnostic 写回同一满队列时死锁。

2. 第一版背压策略采用 bounded memory + blocking：
   - queue 未满时 reader 继续。
   - queue 满时 `write_event` 阻塞等待 flush。
   - 最大阻塞建议值：单次 `write_event` 等待不超过 5 秒；`close()` 总等待不超过 30 秒；append retry 最多 3 次，退避 0.25s/1s/3s。实施可调整，但必须写入 config/default 并测试。
   - 阻塞超过预算后进入 fail-fast：停止接受新 non-terminal events，记录本地 log，构造 terminal diagnostic events，经 `finish_execution(status=failed,error_code="event_flush_failed")` 提交。
   - 若 `finish_execution` 也不可用，则用最后手段 `PATCH status=failed,error_code=event_flush_failed,error_detail=...` 暴露失败；此 debug escape 必须打 `terminal_barrier_failed` log，且不得标记 succeeded。
   - 暂不做 disk spool；若真实 SSH/Pi E2E 证明阻塞会伤害 worker，再升级。

3. 诊断与 metrics schema：
   - log code 枚举：`append_timeout`、`idempotent_replay`、`event_key_conflict`、`queue_full`、`terminal_barrier_failed`、`finish_timeout`、`heartbeat_delayed`、`heartbeat_cancelled`。
   - diagnostic event payload 至少包含：`code`、`execution_id`、`batch_id`、`attempt`、`duration_ms`、`queue_length`、`queue_age_ms`、`failed_flushes`、`last_successful_flush_at`、`timeout_kind`。
   - batch id 由 EventSink 生成，日志和 diagnostic event 共用，方便把 dispatcher log 与 server event 对齐。

4. 实现 terminal close：
   - `close(terminal_status=...)` 只负责 flush projector 与组织 terminal events。
   - 调用 `client.finish_execution()` 一次性提交 terminal events + patch。
   - finish 失败时返回 failure，调用方不得标记 success。

5. 改 `questions.py`：
   - 去掉未检查 `ok` 的 direct final append 主路径。
   - canonical final 优先来自 projector close。
   - fallback final 由 sink terminal events 统一提交，event_key 固定为 `{execution_id}:assistant:final`。
   - 顺序必须是 stream drain -> final fallback -> terminal status -> finish。
   - fallback final 与 projector final 必须共用 `stream_key` 或明确 priority；同一回答不得在 UI 中重复显示。

6. 改 `common.py`、`explore.py`、`bootstrap.py`、`healthcheck.py`：
   - terminal 路径迁到 `finish_execution`。
   - postprocess failure diagnostic 也检查 append/finish 返回。

7. 改 `CairnClient`：
   - 增加 `finish_execution()`。
   - 可对 event append / finish 使用更明确 timeout budget，但不得作为唯一修复。

PYTHONPATH=cairn/src python -m pytest \

### 验收

- append timeout 后 batch 可重试且不重复。
- `/events` 首次 timeout 但 server 已写入时，重试后无重复，日志出现 `append_timeout` 与 `idempotent_replay`。
- 连续 timeout 时 queue 有上限，execution 不得 `succeeded`，events 或 patch 中可见 `event_flush_failed`。
- finish timeout 或 conflict 不会产生 succeeded execution。
- question final 不静默丢失。

### 审查点

- 若 `close()` 内部吞掉 finish 失败并返回 success，停止。
- 若 queue 无限增长，停止。
- 若 fallback final 与 projector final 可重复显示，停止。

## Phase 4: Heartbeat / Scheduler 背压隔离

### 目的

避免 event append 背压拖死 heartbeat，造成“远端还在干活，本地以为断了或杀了”。

### 步骤

1. 审查 `HeartbeatLease` 当前 failure 逻辑：
   - 区分 server timeout、HTTP 5xx、worker process failure。
   - 记录 heartbeat delayed diagnostic。
   - `HeartbeatLease.for_execution` 或等价构造必须接收 diagnostic writer；若 heartbeat 线程不能直接 append events，则在 cancellation/terminal finish 时汇总 heartbeat failures 生成 system diagnostic event。

2. 调整 heartbeat budget：
   - heartbeat request timeout 不与 event append 完全共享。
   - heartbeat grace 至少覆盖一次 event append close/flush 最大等待。
   - 连续 heartbeat timeout 只触发 cancellation 时必须写 diagnostic。

3. Scheduler claim/healthcheck 限流：
   - healthcheck claim 不得在已有大量 running/event backlog 时挤占全部 worker。
   - manual healthcheck event 写失败必须可见，不影响 unrelated question execution terminal barrier。

4. 增加 dispatcher loop logging：
   - append timeout、finish timeout、heartbeat delayed、queue full 单独 log code。
   - heartbeat diagnostic payload 使用 Phase 3 相同 schema，至少带 `code=heartbeat_delayed|heartbeat_cancelled`、`execution_id`、`attempt`、`duration_ms`、`timeout_kind`。

- 若最终取消 worker，execution events 中有 system diagnostic。
- 若 heartbeat 失败只写本地 log、execution events/error_detail 不可见，验收失败。
- healthcheck 背压不影响 question final delivery。

### 审查点

- 若只是把 heartbeat timeout 调到很大而无诊断，停止。
- 若 healthcheck 与 question 同优先级抢占导致饥饿，停止。

## Phase 5: UI Cursor Projection 修复

### 目的

在不等待 V3.3 的前提下，修复现有 UI 的长输出截断、固定轮询上限、raw JSONL 双投影。

### 步骤

1. Phase 5a：抽出 UI 事件读取与 projection helper：
   - `loadAllExecutionEvents(projectId, executionId, limit)`
   - `loadAllBranchTimeline(projectId, branchId, limit)`
   - 循环 `after_cursor` 到无新 events 或达到安全页数。
   - 先用 JS DOM 或静态 guard tests 覆盖 helper 行为，再接入 polling lifecycle。

2. Phase 5b：修复 `loadSelectedConversation()`：
   - 初载读取完整 execution semantic events，至少保证 tail final/status 可见。
   - 对 running execution 使用 cursor 增量，不每秒重拉头页。

3. Phase 5c：修复 `pollQuestionThread()`：
   - 去掉固定 `120 * 1.5s` 静默上限。
   - 轮询到 execution terminal；若超过 UI 最大等待，显示“仍在运行，可恢复轮询”，不清掉 active job。
   - branch timeline 使用 cursor 增量。

4. 移除 Conversation 主路径 raw JSONL parser：
   - `executionEventToConversationEvents(stdout)` 在 Conversation view 中只返回 raw/debug，不解析 backend-specific JSON。
   - `workerJsonLinesToConversationEvents` 删除，或仅保留 `raw/debug` 明名函数且不被 Conversation 主路径调用。
   - 增加 Raw view 与 Conversation view 分离测试：同一 stdout JSONL 在 Raw view 可见，在 Conversation view 不生成 assistant message。

5. 保留 Raw view：
   - stdout/stderr 仍可查看。
   - 若 events 太多，可显示 omitted/truncated。

6. 修复 compact 规则：
   - final assistant 与 running partial 使用统一 `stream_key`。
   - terminal status 不覆盖 assistant final。

## Phase 6: SSH / Pi 行为验证与最小加固

### 目的

## 风险与开放问题

1. `finish_execution` API 是新增 dispatcher contract。收益是 terminal 原子性清晰；代价是 touching server/client/task 多处。该代价值得付。
2. 第一版 EventSink 选择 bounded blocking，不做 disk spool。此策略必须有最大阻塞时长、fail-fast fallback、diagnostic schema。若真实 Pi 大量输出时阻塞 SSH reader 导致 worker 卡住，应升级到 bounded disk spool。
3. 现有 UI 是单文件 Alpine，增量 cursor 逻辑会增加复杂度。因 V3.3 暂跳过，需用 guard tests 控制熵增。
4. SSH `readline()` 可能仍造成无换行时的“看似停住”。本轮先把可靠落库和 final 修好，再用真实 E2E 决定是否改 chunk reader。
5. 当前工作区已有 `event_sink.py` 与 `test_v32_execution_event_stream.py` 未归因修改；实施时必须先确认这些修改是否属于用户临时补丁，并在其基础上前进，不回滚。
